# Ship an emberloop-rs change

Steps, in order:

1. Read the AGENTS.md chain for every crate you touch before editing. Write the failing test first, then fix.
2. Run focused tests while iterating (`cargo test -p <crate> --lib`; for UI changes `bun run test` and `bun run check` inside `web/` — this repo is bun-only, never npm or pnpm). If you touched anything under `web/src`, run `bun run build` in `web/` first: the nextest test `the_embedded_web_bundle_is_newer_than_its_sources` fails on a `web/build` older than the sources. Then run `scripts/check` with `background: true` and wait once. It must pass unchanged; never weaken it. Its `openapi` stage rewrites `openapi.json` and `web/src/lib/api/schema.d.ts`; the `generated` stage is a bare `git diff --exit-code` on those two paths, so it compares the working tree with the index and a fresh regeneration fails until the files are staged (`git add openapi.json web/src/lib/api/schema.d.ts`). Staging is enough; ask before committing.
3. Build the release with `EMBERLOOP_HOME=<data root> HOME=<real home> scripts/release`. Set both variables explicitly: a Session HOME can be a harness-private directory, and the default home lookup then fails. The script stops at `release <version> written to target/release-dist` and says it is not published: publishing uploads the artifact outward, so it stays the user's decision — do not add `--publish` unless they asked, and state that it was not published in the reply. When they ask for the publish afterwards, pin the version you already built and deployed (`EMBERLOOP_VERSION=<version> EMBERLOOP_HOME=<data root> HOME=<real home> bash scripts/release --publish`): without the pin the script reads the installed version through `update --next-version`, so it rebuilds and publishes a number no daemon ever ran while the installed one stays older. `--publish` re-runs the whole build (bun install, web build, cargo release build, a couple of minutes), so give it `background: true` and wait once. Verify with `gh release list --repo ciokyyy/emberloop-rs --limit 3` and `curl -sL <asset url>`; `gh release view --json isLatest` is rejected (`Unknown JSON field: "isLatest"`), and a plain `curl -s` prints an empty body because GitHub answers the download with a redirect. A rebuilt binary never matches the installed one byte for byte even from the same tree, so compare the artifact's `--version`, not its hash, and ignore the `Compiling emberloop-daemon v<cargo version>` line: the release number arrives through `EMBERLOOP_BUILD_VERSION`, not `Cargo.toml`.
4. Install with `target/release/emberloop-daemon --data-root <data root> update --file "$PWD/target/release/emberloop-daemon" --session <current session id>`. The command only queues the update: it prints `Update X -> Y is queued`, and the daemon installs and restarts once the session is idle. Do step 5 after that restart, not right after the command.
5. Verify: `readlink <data root>/current` names the new release, `emberloop-daemon --version` matches, and `curl localhost:3000/api/version` agrees. For a `web/` change, prove the code reached the served bundle before reporting success: grep `web/build` for a string or rule your change introduced (`grep -rl` over `_app/`; CSS rules live in `_app/immutable/assets/*.css`); for a dependency-only change with no unique string, use any fingerprinted `_app/immutable` artifact instead; `curl` that artifact from the daemon and compare its `md5sum` with the file in `web/build` (also `md5sum` the release artifact against `<data root>/current/emberloop-daemon`: a matching version string can hide a different binary), then measure the live page at `http://127.0.0.1:3000/...` with `agent-browser` rather than the dev server. Load the heaviest Session you have and step through three Session URLs of one project (`/p/<projectId>/s/<sessionId>` from `GET /api/sessions`, asserting `location.pathname` matches because `/session/<id>` and `/sessions/<id>` redirect to the project's latest Session) and `document.querySelector('main').innerText.length > 0` after each: the update restart errors every open EventSource at once, which is exactly when a stale-stream bug surfaces. Check main text, not feed rows — a large Session shows no mounted rows for several seconds while the virtualizer fills. For an installable app, also check `navigator.serviceWorker.getRegistration('/')` in that page reports an `activated` worker whose scope is the origin root. The project status page `/p/<projectId>/status` mounts `main` immediately with `Loading system status…` before `/api/status/system` resolves (`/api/status` alone returns 404), so wait with `agent-browser wait --text "v<version>"` rather than `wait main`; once settled it prints `v<version>` in `document.querySelector('main').innerText`, one read that proves bundle and API agree after a restart; the root `/status` renders only `Select a Project`. A new SSE route is proven live with `curl -s --max-time 3 -D - -o /tmp/frames.txt <url>`: the timeout stops the never-ending body with exit 28 while the file holds the status line and the seeded frames, so assert `content-type: text/event-stream`, then the frame ids and states you expect.
6. For a behavior change that reaches a live model, test it on a real Session. See `references/live-session-testing.md` for the endpoints, steer route check, and polling method. When the change is to a tool the Session itself calls, the Session that resumes after the update restart already runs against the new daemon: call the tool directly with the new argument and check its result and side effects instead of building an HTTP probe. For a change to how much a tool returns, measure in one `execute` script: the answer's byte length, whether the harness truncation marker (`truncated output`) is absent, and the continuation offset the answer names, then follow that offset once and measure the next page the same way — three facts that prove paging works without pulling a whole page into your own context.

Delegation: when the user says to let agents do the fix, `spawn` a `worker` at `tier: "mid"` (or `smol` for a mechanical change); never `top` unless asked. Stop editing the files you hand over. The brief names the repo root, the skills to read first (`web/AGENTS.md`, `emberloop-rs-web-ui`), the exact state already changed, the checks to run (`bun run test` with `background: true`, because the web suite outlives a foreground call), what is off limits (release build, daemon restart, untouched components) and a short report format. Then wait for its report instead of re-running its checks. A worker error report (`upstream error: error decoding response body`) arrives while the harness is already retrying the run itself (its own `Retrying (attempt n/3…)` notice) and can land after the worker resumed: call `result` and read `active`, then wait. Do not `steer` a worker because of that error: a steer only injects an extra user turn into the retried run and looks like a resume that did not happen. If a worker ends idle with the error after its retries, give a fresh `spawn` a brief that names the files already changed. `steer` with a new `tier` returns `409 Conflict` while a turn runs, so switch tiers only when idle.

Pitfalls:
- The bash tool refuses shell redirects (`> file`, `2>&1`). Run `scripts/check` and `scripts/release` with `background: true` and no redirect, then wait on the handle and read its log path. Foreground `bash` calls default to a 120s timeout and are clamped by `EMBERLOOP_MAX_CALL_SECS=170` under Antigravity even if a higher `timeout` is passed, so never chain `cargo clippy`, multiple `cargo test -p` crates, and `web/` checks in one foreground command; split checks per crate or use `background: true`. A cold `cargo test -p <crate>` spends a minute compiling and then dies on the foreground timeout, so give every cross-crate run `background: true`. Never end a check with `| tail -N`: the handle keeps only those lines and reports the pipeline's last command so `tail`'s exit status hides a red suite, and a test name missing from a truncated log is not evidence it did not run. Prove a specific test by running it alone with a name filter (`cargo test -p <crate> --test <file> <filter>`) and read that run's result.
- A daemon update restarts every Session process, so reviewer Sessions (`spawn` spec/standards) go inactive with no report. After the restart call `result` on each, then `steer` it with the same `ticketPath` and `startingPoint` to re-review; do not respawn.
- Do not kill the daemon by hand while any Session works; use the `update` command so the restart is orderly.
- Run `cargo fmt --all -- --check` first and list the `Diff in <file>` lines. Format only those files (`rustfmt --edition 2021 <file>`, matching the workspace edition), not the whole tree: `cargo fmt --all` reformats unrelated uncommitted files. Calling bare `rustfmt <file>` can fail in Rust 2015 mode. Keep `pub mod` lines alphabetical; rustfmt reorders them and fails `scripts/check`'s fmt stage otherwise.
- `scripts/check` launches each stage in the background and prints its verdict only at the end; one printed tail can hide green stages. Read `target/<stage>.log` and `target/*.failed` for the stages you care about. A cold first run can also break the total budget in `scripts/check-budget.tsv` while every stage passed (a cold compile is minutes); rerun warm and judge the budget line separately from stage results.
- A red stage is not automatically yours: the failure tail can name a crate or advisory your diff never touched. Re-run that stage alone for its full reason (`cargo deny check | grep -n 'FAILED\|^error'`), compare it against `git diff --stat`, and report a pre-existing `error[unmaintained]` advisory instead of adding an ignore to `deny.toml`, which is a dependency decision the user owns.
- Every harness start waits on a ready handshake: the ACP driver sends `(session_id, options, resumed)` to the waiter once `session/new` returns. An edit in that block that drops the send makes every harness start hang until the timeout (13 nextest timeouts plus one acceptance failure), while unit tests that never start a harness still pass. After editing harness start code, look for the timeout count before trusting a green focused test run.
- A new required prop on a Svelte component breaks every existing test mount with a type error in `svelte-check`. Give new props a default (`onskills = () => {}`) unless every caller must pass one.
- A new required field on a schema-generated type (`UsageRecord`, `Session`, …) breaks every fixture that builds one by hand, and `svelte-check` reports only the first. Regenerate `openapi.json` and `web/src/lib/api/schema.d.ts` quickly while iterating with `cargo run -p api --bin dump_openapi && (cd web && bun run generate:api)`, then grep the type name across `web/src` (`grep -rln UsageRecord web/src`) and update every test helper (defaulted parameters keep existing cases unchanged).
- Read the failing test's assertion before changing behavior: a test that pins the old behavior (e.g. a 409 for a feature being replaced) must be rewritten to the new contract, not left failing.
- `SessionRunner` caches live harness handles by Session ID in `handles`: mutating `SessionMeta` (such as subagent role or model) and re-prompting the same test Session ID reuses the cached handle and skips building new `HarnessWiring` env. Insert and prompt a fresh Session ID per wiring case.
- A Session that started before the update has no frozen skill catalog (`<session>/skill-catalog.md` is written only when a Session starts). Say so; do not call it a bug.
- Clippy enforces `cognitive-complexity-threshold = 15` and denies `tokio::time::sleep` / `std::thread::sleep` workspace-wide (`clippy.toml`, in both library and test targets): for genuine production retry/backoff timers, inject durations (passing `Duration::ZERO` in tests) and isolate the sleep inside a small helper annotated with `#[allow(clippy::disallowed_methods)]`; in async tests, replace sleeps with bounded `tokio::task::yield_now().await` loops (live-model tests may use `#![allow(clippy::disallowed_methods)]`).
- To prove a proxy feature keeps the provider cache intact, run an `#[ignore]` live test (pattern: `crates/daemon/tests/review_live.rs`, `LIVE_CLAUDE_HOME`, `LIVE_CLAUDE_BIN`) and compare `(input, cached, created)` of the proxy `usage` events before and after the feature's side request. In an API test, call `state.models.refresh().await` before `PUT /api/settings`; without a catalogue the title-model check answers 400. A PUT now also writes `<data root>/settings.json`, so a test that changes settings leaves that file behind and a restart test loads it with a second `AppState` on the same data root.
- Changing a value in `Settings::default()` (`crates/api/src/state.rs`) reaches only data roots with no `settings.json`: every save writes the whole struct, so any root that ever saved keeps its stored value and the running daemon never sees the new default. Say so in the plan and the reply. Then ask the user to pick: they move the Settings slider, or the agent changes the value through the API, or the stored value stays. Never hand-edit `settings.json`: the daemon loads it once at start into memory and does not reread it, so its next save overwrites the edit. API path: GET `localhost:3000/api/settings`, change only the one field, PUT the whole object back (one `execute` script with stdlib `urllib`; no token needed). The PUT takes the full `Settings` body, so a partial object resets every other field. The PUT checks `title_model` and `default_model` against the catalogue first (400 `Unknown model: <id>`), so a 400 means a stored model is invalid and nothing was written. Confirm with a second GET. A default change also moves `openapi.json`, `web/src/lib/api/schema.d.ts`, `web/src/routes/+layout.svelte` initial state, `Settings.test.ts` fixtures and `docs/architecture.md`; grep the field name across `crates web/src docs openapi.json`.
- Never write a release number into a plan or reply ahead of the build: `scripts/release` takes the next number from the installed daemon (`update --next-version`), so read `curl -s localhost:3000/api/version` first.
- A new proxy event payload must keep the shape its web reader expects (e.g. `skill-review` `ops` is a flat op list, not the call's `{ops}` wrapper). Test the emitted event data, not only that the event fired.
- A change to `reset_history` semantics (history now carried across a reset) breaks tests that assert the old restart; rewrite those to the new contract. Same-role merges in `carry` are needed because several wires refuse two turns of one role in a row.
- Probing the agy ACP server (`agy_acp_server.par`) by hand: set `GEMINI_HOME` to `<config>/accounts/agy/default`, not `accounts/agy`, or it answers `Authentication required`. `session/new` makes three sequential Google calls (token refresh, loadCodeAssist, fetchAvailableModels) and can take 20s+ on a slow-DNS host; `crates/harness-acp/src/lib.rs` waits on `SESSION_READY_TIMEOUT` (180s) for session creation. Check `curl -w %{time_namelookup}` before blaming auth.
- The daemon's tracing must write to stderr: the `mcp` subcommand (spawned by agy/claude/pi harnesses, inheriting `RUST_LOG`) speaks JSON-RPC on stdout, and a log line there breaks the harness's `tools/list`. Test with `crates/daemon/tests/mcp_stdout.rs`.
- Google (agy) streams repeat `usageMetadata` per chunk and early readings lack `cachedContentTokenCount`; the proxy holds the newest reading and publishes once at stream end (`SseState::held`). Two usage events per step, cached 0 then ~90%, mean a metering regression, not a cache invalidation. A one-off red that repeats green is load flake: `background_loads_the_runtime_env_file_too` and `harness-pi::pi the_session_home_points_pi_at_the_proxy_and_the_tools` both spawn a binary. Confirm with `cargo nextest run --workspace` before investigating.
- `git stash` on one file in a dirty tree is unsafe for a red/green check; prove red by reasoning or a temporary edit instead.
- nextest's default `slow-timeout = { period = "4s", terminate-after = 1 }` kills a test that spawns a binary under load: it FAILs in a fraction of a second with no captured output, then passes alone. Do not rerun until green. `.config/nextest.toml` overrides `filter = "binary(pi)"` with `threads-required = "num-cpus"` and a 20s period, because that binary also sets a process environment variable and racing tests in it share it.
- A TIMEOUT at exactly 4s for a test that takes milliseconds alone is not automatically load: look for an unbounded `recv().await`. A broadcast channel delivers only events published after `subscribe()`, so subscribing after the action and then awaiting hangs whenever the publisher wins the race; move `subscribe()` before the action.
- A test that asserts an exact prompt or notification count after waiting for one visible side effect races the consumer that drains it: make that path deterministic (e.g. `queue.set_turn_active(true)` keeps a queued report from being idle-delivered through `driver.prompt`) and assert afterwards, instead of loosening the expected count.
- Daemon acceptance tests using a temp `data_root` that call `/api/models/refresh` or construct `AgyHarness` without needing real `agy` must place a failing stub at `<data_root>/agy-acp/1.4.5/agy_acp_server.par` (`#!/bin/sh\nexit 1`), because `resolve_bin` falls back to `default_data_root()` and otherwise launches the host's real PAR binary past nextest's 4s `slow-timeout`.
- `scripts/check` prints `budget exceeded: <stage> <ms> > <budget>` in its closing table even when every stage passed. The web stage re-runs in full whenever any `web/src` file changed, so an overrun there is a measured fact, not a flake: time its sub-commands (`svelte-check`, `fallow`, `vitest`, `vite build`) before calling the host slow. Vitest's default forked pool re-paid the Svelte compile per worker file, which put the stage at 224 s against a 180 s budget; `pool: "threads"` in `web/vite.config.ts` brought it to 163 s. Never raise the budget to make a change pass.
- Svelte/Tailwind work in `web/`: load the `emberloop-rs-web-ui` skill for the token list, mobile layout habits and jsdom stubs.
- Another agent may be working in the same checkout. Read `git diff -- <file>` for every file you changed before staging: a file where you only edited a doc comment can carry their code hunks. Stage your own hunks only, or leave the change uncommitted and tell the user which files are yours. Never `git add -A` in a shared tree. Recipe for separating the hunks: `references/shared-tree-commits.md`. Their half-finished edit also breaks the crate build: when `cargo test -p <crate>` fails to compile inside a file you did not touch (e.g. `module_of` not found in `skills.rs` tests), run only your target (`cargo test -p <crate> --test <name> <filter>`) and report the blocked check instead of fixing their file. That escape hatch is useless for a `--lib` test: the lib target compiles every module of the crate, so their broken file blocks your focused run too. Do the compile-free work meanwhile (prompt markdown, `rustfmt --edition 2021 --check <file>`) and retry the focused test in a bounded loop (`for i in $(seq 1 12); do sleep 20; cargo test -p <crate> --lib <filter>; done`, stop at the first run that reports `test result`), because their WIP usually lands within minutes.
- A test fixture or helper another worker added in a shared tree is a contract: grep every use in the crate before deleting or reshaping it (`broken_body`, a stream stub). Their tests still call it, and the missing field fails `cargo test -p <crate> --lib` under your name. Re-read a file right before the patch as well: a view taken minutes earlier can already hold their rewrite, and the anchors then land in the wrong block.
- A proxy fault test that needs a truncated provider body cannot use the axum fake upstream: hyper panics on a body shorter than its declared content-length (`payload claims content-length of 92, custom content-length header claims 4096`) and the client fails at `send()` with `IncompleteMessage` (`Kind::Request`), not the production `error decoding response body` (`Kind::Decode`). Recipe, plus how a dropped body must be worded so the subagent supervisor retries instead of failing the worker: `references/proxy-failure-fixtures.md`.
- A checkpoint commit of a mixed checkout is several commits, one area each, staged by explicit path: `crates/api`+`crates/daemon`+`crates/tools` with the generated `openapi.json` and `schema.d.ts`, then `crates/proxy`, then `web/src` with `design.md`/`design.figcraft`, then the `.agents` skills. Run `scripts/check` before committing, since its `generated` stage compares the index and needs the generated pair staged anyway, and confirm the set with `git diff --cached --stat` (`git status` has no `--cached` flag). Name a changed user-visible default in the body (`max_context_limit` 75 to 20, `emergency_threshold_percent` 95 to 25): a default buried in a diff is invisible to whoever reads the log. Put the agent byproducts in `.gitignore` first (`/.tmp`, `/.scratch`, `/.claude`, `.agents/skills/.backup`, `.agents/skills/.locks`), or the checkpoint's `git add -A <dir>` sweeps tool output and skill backups into the tree.
- Adding a harness tool, a prompt id or an API route touches a long fixed list of files (pinned test lists, three daemon config builders, the review whitelist, generated OpenAPI). Walk `references/new-harness-tool.md` before the first edit.
- Changing a tool's model-facing behaviour reaches five places before it is done: the code, `crates/prompts/prompts/tool.<name>.md`, the inline input schema in `crates/tools/src/mcp.rs`, `_SPECS` (and wrapper `def <name>`) in `crates/tools/src/execute.rs`, and that crate's `AGENTS.md` bullet. `crates/prompts/src/tests.rs` and `crates/tools/tests/contract.rs` police the wording: every backticked word must be a parameter, value or tool name (`bash: \`rtk\` is not a parameter, value or tool`), `contract.rs` advertises with `session_url: None` so subagent tools (`spawn`, `steer`, `stop`, `result`, `submit`) are absent from its `tool_names` set (leave them unbackticked in always-on tool descriptions), and the read path description must keep naming each accepted form (directory, URL, `ctx:<handle>`), so write an external binary or suffix plain. Run `cargo test -p prompts` and `cargo test -p tools` before `scripts/check` to see those contract failures in seconds. Porting behaviour from the Go Emberloop copies its guards and fallbacks exactly, including a test that skips when an external binary is missing.
- A numeric limit or wording on a subagent tool (`submit`) lives outside `crates/tools`: the validator array in `crates/api/src/subagents.rs`, `crates/prompts/prompts/tool.submit.md`, the boundary pair in `crates/api/tests/subagents.rs` (accept at N, reject at N+1, both by `chars().count()`), and the contract line in `specs/phase-2/reviewer-subagents.md`. Bump both test numbers with the limit, or the old number keeps passing.
- Prove a prompt-text change reached the running daemon without a live model run: prompts are `include_str!`-embedded, so `strings <data root>/current/emberloop-daemon | grep -o '<new sentence>'` shows the served text. A spawned probe is the slower proof: a tier whose provider stalls burns the harness timeout (about 300 s) on every retry and every submit nudge, so verify from the binary plus the boundary test and state in the reply that no live model exercised it.
- A hashline `PUT N.=M` replaces its whole range. When the replacement ends a block, include the closing `}` and any attribute line above the first replaced line (`#[derive(...)]`), and re-read the result: a dropped `}` or derive costs a compile cycle. Insert new lines with `PUT >N:`; an insert that ends a block must not repeat the closing `}`, and an insert placed just above a block's final `}` leaves the brace you copied from the body as a second one, so read the returned view before compiling. Use `PUT N.=N:` only when the body is exactly one line, or the leftover tail is dropped/duplicated and the old line above a block (`pub mod x;`, `} = $props();`, `#[utoipa::path(`) is left orphaned. Read the target range in the same turn as the patch and copy its numbers: an estimated anchor on a one-line `PUT N.=N:` replaces the neighbouring field or doc line instead of the one you meant, and only the returned view shows it (a duplicated doc line and a deleted `pub about: String` compile to a different error than you expect). Every patch invalidates the tag it was made with: op numbers belong to the view that produced them, so never reuse numbers from an earlier call, even for the file you just patched — identical `N` addresses a different line once lines above it changed, and the wrong line lands silently unless you read the returned view.
- Model-facing text has two prices. A tool description, `policy`, or `compress` loads on every request of every Session; a nudge loads only when it fires. Put new wording where it is read at the moment it changes behaviour, and keep the always-resident files short.
- The `el://docs` renderers in `crates/tools/src/docs.rs` are `format!` raw strings: every literal `{` or `}` (a JSON sample, anything brace-shaped) must be written `{{`/`}}` or the crate fails with `error: invalid format string` and the hint `if you intended to print `{`, you can escape it using `{{``. Their wording is pinned by `crates/tools/tests/tools.rs` (`read_el_docs_config_shows_paths_but_never_secret_contents`), so grep that test for the section before editing and add an assertion on the new text first; it is a fast red/green that costs seconds.
- A reference doc that names config keys, versions or paths is unverified until each name is grepped in code: a key that exists only in the doc makes the model write invalid config, and hand-written field lists drift. Derive the list from one table in code where possible, and check versions against the constant the daemon pins.
- A Session that idles or will not resume, and a provider that 401s in one agent while working in another, is often account state rather than a bug: check the usage limit and the per-Session credential before reading daemon code. Recipe in `references/provider-auth-and-quota.md`.
- Never assume a fold or review feature works live from unit tests alone. State what was not checked in the final reply.
- Built-in MCP subsystems: do not leave core tools as optional user entries. Use daemon-level `ensure` on `<config root>/mcp.json`, auto-inject session project context in `crates/tools/src/mcpclient.rs`, and keep project-scoped views in a header `•••` right drawer rather than the global sidebar (see `references/baked-in-subsystems.md`).
- Web check health score (`bunx fallow health --score --min-score 87.9`): dead code deductions drop the score below 88. Keep unconsumed helpers private (no `export`), delete or consume unreferenced files, and split complex Svelte views into subcomponents to stay under cognitive complexity limits. The floor is only 0.1 under a healthy tree, so measure the baseline's penalty lines in a throwaway worktree before refactoring anything large: the `unit size` deduction is usually pre-existing debt, not yours (recipe in the `emberloop-rs-web-ui` skill).
- CI steps have an order the tests enforce: any step that regenerates a tracked web source (`bun run generate:api` writes `web/src/lib/api/schema.d.ts`) must run before the Web bundle step, and `bun install --frozen-lockfile` must run before it, or the step exits 127 (`openapi-typescript: command not found`) or `the_embedded_web_bundle_is_newer_than_its_sources` fails after a green build.
- `pi-ai` is a git pin to the `ciokyyy/pi-rust` fork, not a crates.io release. Before reporting a dependency update, check the upstream `yannelli/pi-rust` tag and rebuild the fork patch on it; recipe in `references/pi-ai-pin.md`.
- A full dependency refresh has its own order and breakages: exact workspace pins, Cargo feature renames, and SvelteKit major config moves all need code edits. Recipe in `references/dependency-upgrades.md`.
- `git push` here has no stored https credential and fails with a credential prompt. Push with `git -c credential.helper='!gh auth git-credential' push origin master`.
- When the checkout carries another agent's uncommitted work, document committed behaviour only: read the file at `git show HEAD:<path>`, not the working tree, so a WIP default does not end up in the docs.
- A docs change with Mermaid diagrams is not done until each block renders: `bunx -p @mermaid-js/mermaid-cli@11 mmdc -p puppeteer.json -i d.mmd -o d.svg` with `puppeteer.json` holding `{"args":["--no-sandbox","--disable-setuid-sandbox"]}` (headless Chrome refuses to start as root without it).
- Compiling external dependencies or binaries: `/tmp` can be a small tmpfs (e.g. 5GB at 95% full), causing `collect2: fatal error: ld terminated with signal 7 [Bus error]`. Set `CARGO_TARGET_DIR` on a physical disk partition with sufficient headroom before building.
- A fail-closed shell allowlist (e.g. read-only mode) must split chains/pipelines and argv words in one quote-aware tokenizer pass and validate mutating or external-exec flags per command (`tree -o`, `file -C`, `git grep -O`, `git diff --no-index`, `--textconv`, `rg --hostname-bin`, `cargo --config`): separate passes drift on escaping, and binary-only allowlists leave writes and arbitrary command execution open.

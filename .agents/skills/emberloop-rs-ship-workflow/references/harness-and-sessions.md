# Harness and Session behaviour

Delegation: when the user says to let agents do the fix, `spawn` a `worker` at `tier: "mid"` (or `smol` for a mechanical change); never `top` unless asked. Stop editing the files you hand over. The brief names the repo root, the skills to read first (`web/AGENTS.md`, `emberloop-rs-web-ui`), the exact state already changed, the checks to run (`bun run test` with `background: true`, because the web suite outlives a foreground call), what is off limits (release build, daemon restart, untouched components) and a short report format. Then wait for its report instead of re-running its checks. A worker error report (`upstream error: error decoding response body`) arrives while the harness is already retrying the run itself (its own `Retrying (attempt n/3…)` notice) and can land after the worker resumed: call `result` and read `active`, then wait. Do not `steer` a worker because of that error: a steer only injects an extra user turn into the retried run and looks like a resume that did not happen. If a worker ends idle with the error after its retries, give a fresh `spawn` a brief that names the files already changed. `steer` with a new `tier` returns `409 Conflict` while a turn runs, so switch tiers only when idle.

Pitfalls:
- A daemon update restarts every Session process, so reviewer Sessions (`spawn` spec/standards) go inactive with no report. After the restart call `result` on each, then `steer` it with the same `ticketPath` and `startingPoint` to re-review; do not respawn.
- Every harness start waits on a ready handshake: the ACP driver sends `(session_id, options, resumed)` to the waiter once `session/new` returns. An edit in that block that drops the send makes every harness start hang until the timeout (13 nextest timeouts plus one acceptance failure), while unit tests that never start a harness still pass. After editing harness start code, look for the timeout count before trusting a green focused test run.
- `SessionRunner` caches live harness handles by Session ID in `handles`: mutating `SessionMeta` (such as subagent role or model) and re-prompting the same test Session ID reuses the cached handle and skips building new `HarnessWiring` env. Insert and prompt a fresh Session ID per wiring case.
- Changing a value in `Settings::default()` (`crates/api/src/state.rs`) reaches only data roots with no `settings.json`: every save writes the whole struct, so any root that ever saved keeps its stored value and the running daemon never sees the new default. Say so in the plan and the reply. Then ask the user to pick: they move the Settings slider, or the agent changes the value through the API, or the stored value stays. Never hand-edit `settings.json`: the daemon loads it once at start into memory and does not reread it, so its next save overwrites the edit. API path: GET `localhost:3000/api/settings`, change only the one field, PUT the whole object back (one `execute` script with stdlib `urllib`; no token needed). The PUT takes the full `Settings` body, so a partial object resets every other field. The PUT checks `title_model` and `default_model` against the catalogue first (400 `Unknown model: <id>`), so a 400 means a stored model is invalid and nothing was written. Confirm with a second GET. A default change also moves `openapi.json`, `web/src/lib/api/schema.d.ts`, `web/src/routes/+layout.svelte` initial state, `Settings.test.ts` fixtures and `docs/architecture.md`; grep the field name across `crates web/src docs openapi.json`.
- Probing the agy ACP server (`agy_acp_server.par`) by hand: set `GEMINI_HOME` to `<config>/accounts/agy/default`, not `accounts/agy`, or it answers `Authentication required`. `session/new` makes three sequential Google calls (token refresh, loadCodeAssist, fetchAvailableModels) and can take 20s+ on a slow-DNS host; `crates/harness-acp/src/lib.rs` waits on `SESSION_READY_TIMEOUT` (180s) for session creation. Check `curl -w %{time_namelookup}` before blaming auth.
- The daemon's tracing must write to stderr: the `mcp` subcommand (spawned by agy/claude/pi harnesses, inheriting `RUST_LOG`) speaks JSON-RPC on stdout, and a log line there breaks the harness's `tools/list`. Test with `crates/daemon/tests/mcp_stdout.rs`.
- Google (agy) streams repeat `usageMetadata` per chunk and early readings lack `cachedContentTokenCount`; the proxy holds the newest reading and publishes once at stream end (`SseState::held`). Two usage events per step, cached 0 then ~90%, mean a metering regression, not a cache invalidation. A one-off red that repeats green is load flake: `background_loads_the_runtime_env_file_too` and `harness-pi::pi the_session_home_points_pi_at_the_proxy_and_the_tools` both spawn a binary. Confirm with `cargo nextest run --workspace` before investigating.
- A Session that idles or will not resume, and a provider that 401s in one agent while working in another, is often account state rather than a bug: check the usage limit and the per-Session credential before reading daemon code. Recipe in `references/provider-auth-and-quota.md`.
- Built-in MCP subsystems: do not leave core tools as optional user entries. Use daemon-level `ensure` on `<config root>/mcp.json`, auto-inject session project context in `crates/tools/src/mcpclient.rs`, and keep project-scoped views in a header `•••` right drawer rather than the global sidebar (see `references/baked-in-subsystems.md`).

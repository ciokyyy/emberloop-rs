# Repo edits and commits

Pitfalls:
- Do not kill the daemon by hand while any Session works; use the `update` command so the restart is orderly.
- Another agent may be working in the same checkout. Read `git diff -- <file>` for every file you changed before staging: a file where you only edited a doc comment can carry their code hunks. Stage your own hunks only, or leave the change uncommitted and tell the user which files are yours. Never `git add -A` in a shared tree. Recipe for separating the hunks: `references/shared-tree-commits.md`. Their half-finished edit also breaks the crate build: when `cargo test -p <crate>` fails to compile inside a file you did not touch (e.g. `module_of` not found in `skills.rs` tests), run only your target (`cargo test -p <crate> --test <name> <filter>`) and report the blocked check instead of fixing their file. That escape hatch is useless for a `--lib` test: the lib target compiles every module of the crate, so their broken file blocks your focused run too. Do the compile-free work meanwhile (prompt markdown, `rustfmt --edition 2021 --check <file>`) and retry the focused test in a bounded loop (`for i in $(seq 1 12); do sleep 20; cargo test -p <crate> --lib <filter>; done`, stop at the first run that reports `test result`), because their WIP usually lands within minutes.
- A test fixture or helper another worker added in a shared tree is a contract: grep every use in the crate before deleting or reshaping it (`broken_body`, a stream stub). Their tests still call it, and the missing field fails `cargo test -p <crate> --lib` under your name. Re-read a file right before the patch as well: a view taken minutes earlier can already hold their rewrite, and the anchors then land in the wrong block.
- A checkpoint commit of a mixed checkout is several commits, one area each, staged by explicit path: `crates/api`+`crates/daemon`+`crates/tools` with the generated `openapi.json` and `schema.d.ts`, then `crates/proxy`, then `web/src` with `design.md`/`design.figcraft`, then the `.agents` skills. Run `scripts/check` before committing, since its `generated` stage compares the index and needs the generated pair staged anyway, and confirm the set with `git diff --cached --stat` (`git status` has no `--cached` flag). Name a changed user-visible default in the body (`max_context_limit` 75 to 20, `emergency_threshold_percent` 95 to 25): a default buried in a diff is invisible to whoever reads the log. Put the agent byproducts in `.gitignore` first (`/.tmp`, `/.scratch`, `/.claude`, `.agents/skills/.backup`, `.agents/skills/.locks`), or the checkpoint's `git add -A <dir>` sweeps tool output and skill backups into the tree.
- A hashline `PUT N.=M` replaces its whole range. When the replacement ends a block, include the closing `}` and any attribute line above the first replaced line (`#[derive(...)]`), and re-read the result: a dropped `}` or derive costs a compile cycle. Insert new lines with `PUT >N:`; an insert that ends a block must not repeat the closing `}`, and an insert placed just above a block's final `}` leaves the brace you copied from the body as a second one, so read the returned view before compiling. Use `PUT N.=N:` only when the body is exactly one line, or the leftover tail is dropped/duplicated and the old line above a block (`pub mod x;`, `} = $props();`, `#[utoipa::path(`) is left orphaned. Read the target range in the same turn as the patch and copy its numbers: an estimated anchor on a one-line `PUT N.=N:` replaces the neighbouring field or doc line instead of the one you meant, and only the returned view shows it (a duplicated doc line and a deleted `pub about: String` compile to a different error than you expect). Every patch invalidates the tag it was made with: op numbers belong to the view that produced them, so never reuse numbers from an earlier call, even for the file you just patched — identical `N` addresses a different line once lines above it changed, and the wrong line lands silently unless you read the returned view.
- `git push` here has no stored https credential and fails with a credential prompt. Push with `git -c credential.helper='!gh auth git-credential' push origin master`.
- When the checkout carries another agent's uncommitted work, document committed behaviour only: read the file at `git show HEAD:<path>`, not the working tree, so a WIP default does not end up in the docs.
- A docs change with Mermaid diagrams is not done until each block renders: `bunx -p @mermaid-js/mermaid-cli@11 mmdc -p puppeteer.json -i d.mmd -o d.svg` with `puppeteer.json` holding `{"args":["--no-sandbox","--disable-setuid-sandbox"]}` (headless Chrome refuses to start as root without it).
- Compiling external dependencies or binaries: `/tmp` can be a small tmpfs (e.g. 5GB at 95% full), causing `collect2: fatal error: ld terminated with signal 7 [Bus error]`. Set `CARGO_TARGET_DIR` on a physical disk partition with sufficient headroom before building.
- A fail-closed shell allowlist (e.g. read-only mode) must split chains/pipelines and argv words in one quote-aware tokenizer pass and validate mutating or external-exec flags per command (`tree -o`, `file -C`, `git grep -O`, `git diff --no-index`, `--textconv`, `rg --hostname-bin`, `cargo --config`): separate passes drift on escaping, and binary-only allowlists leave writes and arbitrary command execution open.

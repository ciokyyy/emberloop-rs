# Porting a third-party skill pack into emberloop-rs

## Procedure

1. **Read the pack's host docs before designing.** Read its README, per-harness docs (`docs/claude.md`, `docs/codex.md`, `docs/harnesses.md`), manifests and at least one agent file. A pack is one root directory (`skills/`, `agents/`, `resources/`, `docs/`); each host resolves that root itself (Claude substitutes `${CLAUDE_PLUGIN_ROOT}`, Codex says three parents above `SKILL.md`). Skills read `agents/` and `resources/` at run time, so copying `skills/` alone breaks the pack.
2. **Ask the scope early.** One named pack is not a plugin system. Do not build manifest, marketplace or `owner/repo` install support unless the User asks; vendor the directory instead.
3. **Install unmodified plus files of ours.** For one pack used as-is: copy the whole upstream directory under a skill root, add one index `SKILL.md` and a `docs/emberloop.md` (root rule, tool mapping, sequencing), and leave upstream files unedited so they stay diffable. For several packs merged into one pipeline (the user's preferred shape, see step 7): rewrite the rules into our own `SKILL.md` files and copy only the runtime assets unmodified (persona `agents/`, `resources/document_standards/`, debugging/test `references/`, each pack's LICENSE). Either way record upstream URL, commit and licence in a NOTICE that lists unmodified, modified and omitted files (Apache-2.0 requires modified files to be marked), plus one `UPSTREAM.md` table for manual re-sync; the user updates from upstream by hand, not by tooling. Before porting a rule or checklist from upstream, check `crates/prompts/prompts/` as well as existing skills so rules already enforced by built-in proxy or reviewer prompts are not duplicated.
4. **Map host tool names.** `Agent`, `spawn_agent` and `invoke_subagent` become `spawn`. Emberloop subagents cannot call `spawn`, `steer`, `stop` or `result`, so a pack step that nests (a synthesizer spawning reviewers) is replaced by direct dispatch from the parent.
5. **Do not rely on `disable-model-invocation`; fold sub-skills and cap index size.** Emberloop has no `Skill` tool and the web composer has no slash commands, so `disable-model-invocation` has no effect. Put rigid sub-skills under `references/` or `skills/` inside one directory, or list competing/secondary skills in `skill-modules.json` (`skills::catalog` strips module members from the top-level list and caps ungrouped lines at `50`). Module membership resolves by skill name after `skills::modules()` merges both roots, so the global `skill-modules.json` already groups same-named project copies; do not duplicate entries in the project file. Modules hide from the catalog only, not from `skill_search` (BM25 over every skill on disk), so a truly competing skill must be deleted. `SEARCH_BODY_BYTES = 2048` limits only what `skill_search` indexes, not what a Session reads: put key triggers in the `150`-char `description`, `#` headings and the first `2048` bytes, and let the body run as long as the procedure needs.
6. **Check subagent isolation in code, not in the pack's prose.** Before trusting a "fresh reviewer", read what the child really gets: the proxy appends every pinned prompt (policy, style prompts, superpowers, skills catalog) to each Session, `scout` drops only `edit` and `write` (it keeps `bash` and `execute`), and Session directories under the data root are readable with `read`. A pack that promises read-only or history-free reviewers needs those gaps closed, with a test. Close the read gap with an allowlist (Project, skill roots, the child's own Session dir), never a `sessions/`-only blocklist: parent transcripts also live in the harness homes (`claude-homes/<id>`, `pi-homes/<id>`) under the data root. Upstream "plugin support" for a host proves install and discovery, not instruction-file exclusion; judge each harness (claude, agy, pi) from its launch code in `crates/harness-*` (working directory, native tools, home directory, env), then add a live-wire probe that plants a marker instruction file and asks the child to quote any instructions beyond its persona.
7. **Combining packs into one workflow: one router, guarded.** Prefer adapting the existing index the bootstrap prompt already points at (`ember-flow/SKILL.md`) over adding a second router skill: the path `el://skills/ember-flow/SKILL.md` is pinned in `crates/prompts/src/tests.rs` and `crates/proxy/src/tests.rs`, and two routers recreate the ambiguity. The `superpowers` prompt is compiled into the binary and reaches every project and every non-goldfish role, workers and scouts included, so the router must live in the global root and must keep a `<SUBAGENT-STOP>` block, or a delegated worker re-enters the workflow. Global skill roots are not in git: vendor anything you edit under `vendor/<pack>` with an install script (the `scripts/install-ember` pattern), and move deleted skills to an archive outside the skills root (`~/.agents/skills-archive/<date>/<global|project>/<name>/`). Before editing `vendor/<pack>` or running `scripts/install-<pack>`, `diff -rq` each `vendor/<pack>/<name>` against `/root/.agents/skills/<name>` and sync any newer installed edits back into `vendor/<pack>` first: install scripts replace target folders with `rm -rf` and otherwise clobber live `skill_manage` edits. A Session's `$HOME` is its harness home (`claude-homes/<id>`), not the user's, so run install scripts as `HOME=/root scripts/install-<pack>` and `ls /root/.agents/skills` afterwards; a plain run installs where no Session looks. Check `git ls-files vendor/<pack>` before telling a worker to `git rm` it: an untracked vendor folder makes `git rm` fail and `rm -rf` loses it for good. Give the router skill a shared family prefix with its stage skills (`ember-flow`, `ember-grill`, ...) as separate top-level folders, since discovery scans only `<root>/*/SKILL.md`; group the stages in a `skill-modules.json` module and leave the router ungrouped. Before deleting a skill, grep both roots for its name; index skills such as `chief-of-staff` and `setup-matt-pocock-skills` reference others. Give a cleanup worker an explicit retire list, "move, never delete", and a stop rule (a folder whose files a kept skill still reads stays put and is reported). Save `git status --short` before you dispatch it: the working tree usually carries other Sessions' dirty work, and without a baseline you cannot tell its deletions from theirs. Keep each pack's personas in `<skill>/agents/` (`personas::discover` scans there) and changes to a pack's review tiers are a user decision, not alignment.
8. **Verify end to end.** Run one real flow through `emberloop-rs-live-wire-testing` and confirm each subagent reports from its own Session.

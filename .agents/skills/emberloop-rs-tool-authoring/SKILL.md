# Authoring a bundled emberloop-rs tool

One tool lives in five places. Miss one and the tool is invisible, unreachable from `execute`, or fails `cargo test -p tools` on the exact advertised list.

## Procedure

1. **List every surface before editing.**
   - `crates/tools/src/mcp.rs` `tool_specs()`: name plus inline `inputSchema` (and the `read.path`-style description text).
   - `crates/tools/src/lib.rs`: a `dispatch_inner` arm for anything the `execute` bridge may call; an arm in public `call` only for a tool that must stay unreachable from inside `execute`.
   - `crates/tools/src/execute.rs` `_SPECS`: the schema copy that exposes the tool to `tools.<name>` in scripts.
   - `crates/prompts/prompts/tool.<name>.md`: the model-facing body.
   - `crates/tools/AGENTS.md`: one line on the module or behaviour.
2. **Register the description text.** `PROMPT_IDS` and `default_text` in `crates/prompts/src/lib.rs`, the `include_str!` entry in `crates/prompts/src/defaults.rs`, and the name in `OFFERED_TOOLS` in `crates/prompts/src/tests.rs`. A prompt file that exists on disk but is unregistered never reaches the model: descriptions flow through `prompts::tool_name` into `McpServer::with_descriptions`.
3. **Keep the prompt inside the contract.** `crates/tools/tests/contract.rs` builds its tool list from `ToolConfig::new`, where `session_url` is `None`, so conditional tools are absent from the advertised set. In a tool prompt, put backticks only around schema property names, enum values and advertised tool names; a backticked unadvertised tool fails the contract test. A module name is not a tool either: write the python module `tools` plain, because a backticked `tools` fails that same test. Every top-level schema parameter must appear in backticks in the prompt.
4. **Update the exact advertised list.** `mcp_serves_tools_and_errors` in `crates/tools/tests/tools.rs` asserts the full name vector in declaration order; add the new name where `tool_specs()` declares it.
5. **Test at two levels.** One Toolbox-level test and one `McpServer::call` test covering the happy path, each documented error string, and any state the tool writes. A persisted or retried call needs a second call proving the state is re-read, not cached. A tool whose MCP result can carry a non-text block (an image) needs a third: assert the serialized `content` array from the `execute` entry point, because the script path answers text only (see `references/execute-bridge-content.md`).
6. **Verify.** `rustfmt --edition 2021` on the files you touched, then `cargo clippy -p prompts -p tools --all-targets -- -D warnings && cargo test -p prompts -p tools`, then the repo gate (`./scripts/check`). Never run `cargo fmt` at any scope (`-p`, `--all`): it reformats unrelated uncommitted hunks, and in a shared checkout that means rewriting another agent's work.

## Changing a contract value on an existing tool

A published limit (an argument's maximum length, an allowed-format marker) is stated in more places than the validator, and raising it is a cross-crate change even when the diff is one number.

1. **Grep the old value before editing**: `<value>` across `crates`, `crates/prompts/prompts` and `specs`. The hits are the validator literal, the `tool.<name>.md` description, a `specs/` contract sentence, and the boundary tests. A description that keeps the old cap makes the model pre-truncate or retry against a limit that no longer exists.
2. **Move both boundary tests in the same pass**: the reject case at new+1 and the accept case at exactly new. A test file that pins only the rejection leaves the raised cap unproven.
3. **Know where the validator lives before trusting a green contract test.** A tool whose enforcement sits outside `crates/tools` (the subagent `submit` caps in `crates/api/src/subagents.rs`) has no `contract.rs` coverage; its only guard is its own test in `crates/api/tests/`. The refusal message interpolates the limit literal, so error text and validator cannot drift apart.
4. **Check the new size against every reader** before raising it: a field rendered as a paragraph (`SubagentReport.svelte`, and the same summary in the parent steer via `SteerQueue::enqueue_report`) grows harmlessly, while a value rendered into a fixed-width row, a filename, or a per-chunk budget does not.
5. **Update the owning `AGENTS.md` or `specs/` sentence that states the old number**, and say the new cap in the final reply: a limit is user-visible behaviour even when it reads like a constant.

## Changing which paths a tool accepts

The jail in `crates/tools/src/jail.rs` gates every path-taking tool, so widening it is a policy change across `read`, `edit`, `write`, `grep`, `find` and `bash`'s view recording at once.

1. **List the resolver's callers first** (`grep -n 'jail()' crates/tools/src/*.rs`) and decide per tool: a tool that only inspects needs no escape, a tool whose output feeds a follow-up path (`read` feeding `edit`) must move with it.
2. **Keep a paired tool usable.** `edit` refuses a path with no recorded view, so loosening `write` alone leaves edit dead on an existing outside file: widen the reader and the bash view recording in the same pass, or every outside edit must bootstrap with a `write`.
3. **Copy the loosest existing policy, never invent one.** If `read` already accepts a class of paths, widen to exactly that class; an allowlist only one tool has makes the tools disagree about the same path and nobody can say where the boundary is.
4. **Expand `~` yourself**: `~` and `~/x` from `HOME`, `~user` left a literal file name, and a clear error when `HOME` is unset. Shelling out to expand would execute the path.
5. **Move every text that states the policy**: the inline schema in `mcp.rs`, `crates/prompts/prompts/tool.<name>.md`, `_SPECS` in `execute.rs`, the crate `AGENTS.md` Limits bullet, and the docs/spec sentences that still say `inside the project root`.
6. **Grep the whole workspace for tests pinning the old refusal** (`is_err()`, `outside the project root`), not just the crate you edited: a daemon-level test can assert the boundary you just moved and be red only in the full gate. Fix the ones you own; for the rest report the exact replacement lines.

## Pitfalls

- A tool that re-dispatches another tool (retry a stored call, replay an edited request) must call the public `Toolbox::call`, not `call_inner`. An arm that exists only in `call` (`execute` is the current one) is unreachable from the inner dispatcher, so a record naming that tool dies with `unknown tool`.
- A tool whose future can reach itself through another dispatcher forms a recursive async type; return `Pin<Box<dyn Future<Output = ToolResult<T>> + Send + 'a>>` and keep an explicit recursion guard (a thread-local set for the duration of `execute`). The comment on the boxed signature names `Toolbox::call` as the reason.
- Wrap failures only after the denied/allowlist check. Wrapping before it records retry state for a call that can never be permitted, and the model follows a dead `#N`.
- Wrap retry errors exactly once. `call_inner` already calls `wrap_retry_error`, so a new parts-style wrapper must delegate its non-`execute` arm to `call_inner` unwrapped; a second wrap records the failure twice and shifts the `[failed call #N]` ids the retry tests pin.
- A result part that cannot travel as text (an image, binary bytes) is invisible inside `execute` until the bridge carries it: scripts reach tools through `Toolbox::call_inner`, whose reply is a `String`, so a content block built only in `McpServer::call` exists on the direct path alone. See `references/execute-bridge-content.md`.
- Any rendered or schema-adjacent reference text (examples, paths, settings keys, pinned dependency versions, sibling directory names) is an accuracy surface: grep each concrete name against the code that owns it, and give every required value its own assertion. A model that follows a wrong key writes invalid config.
- Never read or echo a secret file from a tool. Render the configured path only, and make the test write a known secret string and assert it is absent from the output.
- Keep every model-facing answer inside the smallest harness cap. pi's MCP bridge hard-cuts any tool result above `MCP_OUTPUT_MAX_BYTES = 20 * 1024` bytes, spills the full text to a `pi-mcp-<hex>.txt` and prepends `Warning: truncated output (original token count: …)`; no setting or `PI_*` variable raises it, so the model silently loses the middle of a long answer and no test goes red. Page the content instead: budget each render at 16 KB (`SKILL_PAGE_BYTES`), end a partial page with a continuation line naming the next offset (`[skill continues at line N: read again with offset N]`), and assert in a test that every page stays under 20 KB and the last page holds the final line. The same budget governs a catalogue view: return the index (name, module, one-line about) and never the bodies, because a read that dumps whole skills truncates the entries furthest down the list.
- A tool that writes a managed JSON state file shared across calls (a module map, an index) must read that file inside the op, never through `seen`: the tool owns it, so there is no user edit to guard and no read-before-write to require. A missing file is empty; an unreadable or malformed one is an error, because reading it as empty makes the rewrite silently discard what it could not parse. Serialize a `BTreeMap` so keys stay sorted and diffs stable, write through `<path>.tmp.<pid>` plus `fs::rename` (the shape `todo.rs` uses), push `Undo::Restore`/`Undo::Remove` before the write so a later failing op restores it, and lock the file name as an extra `(root, "<file>")` key beside the per-name locks, or two concurrent creates lose one entry.
- Gate a new required argument on existing data instead of making it always required: refuse the call without it only when the target or merged state already uses the feature, and list the current choices in the error as `name: about` so one retry can comply. That keeps back-compat tests green and still forces the choice once the system is in use.
- To give a tool a `background` mode, split the work into a `prepare` that builds everything (listener bound, stub written, `Command` assembled, server task spawned) and a thin `run` that spawns, waits and formats, so both modes share one builder. Hand the background process to `BackgroundManager::spawn_with`: its `keepalive: Option<Box<dyn Any + Send>>` drops exactly when the job is reaped (`wait`, `stop`, `refresh_status`), so it owns the in-process server task and its temp dir (an `impl Drop` aborts the task and removes the dir) and `stop` ends them too. Anything that buffered state for a caller must flush on write instead of on exit, because a background script has no caller left to flush it. Give the job `python3 -u` and `exec "$@" 2>&1` with `Stdio::null()` stderr so the log shows output as it lands, add the argument as `#[serde(default)] background: bool` beside its `inputSchema` property, and leave a `shortcut:` comment naming what an adopted job loses when the daemon restarts (the in-process bridge), since `load_adopted` sets `keepalive: None`. Test it end to end: a background script that calls another tool and stores a key, `background` `wait` and `read` for its log, then a fresh foreground call proving the stored key persisted (a buffered store would lose it).
- Config fields that exist only for tests (an allowlist with no setter, a path with no production writer) are speculative generality unless a real caller sets them; name them in the reply instead of adding them.
- Loosening a path policy widens reachability for good: name what the tool can now touch (any file the daemon's user owns, `~/.ssh/*`, the env file holding keys) and which tools still stay inside, in the final reply and in the crate `AGENTS.md` Limits bullet. A silent loosening reads as a bug fix to whoever finds the file later.
- The `crates/prompts/prompts/*.md` files are the repository's default texts, embedded with `include_str!` and shipped with the daemon; editing one is a code change. `prompt_propose` writes the User's live store and never touches these files, so a fix that must land in the repo is a direct file edit, not a proposal.
- Test a `HOME` expansion by overriding `HOME` around the call through an RAII guard that restores it: the variable is process-global, and a leaking override breaks every later path test in the binary.
- When the new boundary needs a test or doc change in a crate another agent owns, report the exact before/after lines instead of editing their file.

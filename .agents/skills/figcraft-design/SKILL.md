# Design in the project's FigCraft file

## Order of work

A redesign request is a FigCraft job first. Draw the screen in `design.figcraft`, save it, and present the board; change the Svelte components after that, from the board. The mock is the review artifact, so a code-first answer is unfinished even when the code works, and a mock still owed must be drawn even after the code shipped. When the ask is whether a screen could look better, ground the answer in the reference products' own docs first (tldraw, Figma Make, the pattern's help pages), name the pattern in one line with its source, then draw it — the user asks for that online verification by name.

Before drawing anything, inventory the document for a frame that already covers the ask — the user often cannot remember whether it exists, and a second copy of the same dialog is worse than none. List the pages with `figcraft.inspect_document {allPages:true}` (page entries give `childCount`, and `get_node` on a page id gives its children) and match by frame name, not by your memory of the file. When a frame already covers the ask, answer with its name, id and geometry, export it at `scale:2` to `.tmp/shots/<name>.png` for the user to look at, and offer to refine or extend it; duplicate only when the user asks for a variant side by side. Answer that inventory question alone: report the frame's name, id and geometry, then stop — never resume an older open design task in the same turn, even one you still owe.

A screen named by a role rather than a frame name (`the editor`, `the dialog`, `the settings page`) can belong to more than one existing screen: this app has a design editor (canvas + agent rail) and a skill editor (SKILL.md). List the candidates from the inventory and say in one line which one you are drawing before the first `node.create`; drawing the sibling costs the whole board and the user has to ask twice.

Never draw a page-title or subtitle text layer: the board already shows the page name, so a title reads as duplicated text. Start content at the page's top-left, and label only what a reader cannot infer — a group of specimens (`Section · TABS`, 10 px SemiBold `--fg-4`, 5 % tracking).

`design.figcraft` in the project root is a MIRROR, not the document. The live document lives in `figcraft-server`; `crates/api/src/design.rs` snapshots it into `design.figcraft` every 5 seconds, so a direct `cp`, unzip/rezip or script write is reverted within seconds. Edit and read it through the MCP server (`figcraft.get_node`, `inspect_document`) and let the snapshot land; unzipping the file to read a frame bypasses the live document, and the user rejects it. When the live session is down, say so and ask before falling back to the file.

## Redesigning a control

When the user rejects a control's look, change the treatment, not its padding or colour. A brand-filled segmented pill becomes an underline tab row: 13 px label (Regular `--fg-3` inactive, SemiBold `--fg-1` active), a 2 px `--brand` underline sized to the label and centred under it, and a 1 px `--border` hairline across the full width. Apply the identical treatment to every mock that shows the control, and update the `Mocks` list in `design.md`, which the repo requires to stay true.

## Screens that fit the existing pages

A content-only frame does not read as a mock of the app: the user asks for it to look like the other pages. Build every new screen on the real shell instead of inventing a new frame:

1. When a finished screen already carries the exact shell and header, duplicate that screen instead of assembling chrome (`edit.duplicate {ids, dx, dy}`, reparent, then delete its body children) and rebuild only the body: fewer steps, and the new screen cannot drift from its sibling.
2. Otherwise duplicate the chrome frames from the chrome page — sidebar (280 px, `#171717`) and session header (720x57, `#1B1B1B`, 1 px `#3B3B3B` divider) — with `edit.duplicate {ids, dx, dy}` (it answers `{ids:[…]}`, and the copy lands on the source page). `node.reparent` each into a new 1000x720 screen frame, then `node.set` its `x`/`y`/`width`/`height`; never redraw the chrome by hand.
3. Mark the active bottom-nav tab the way the chrome page does: fill `#3E3E3E`, label `#FFFFFF`, icon strokes `#FFFFFF`; every other tab `fill:"none"` with `#9E9E9E` label and icon.
4. Override the header title and subtitle texts to the screen's own (a skill name, a path in 11 px JetBrains Mono); the shell header carries the title, so no in-body title row and no page-title layer.
5. Body = one fixed 720x663 frame at (280,57) under the header: `#1B1B1B`, vertical, `gap:16`, `padding:[16,16,16,16]`, `clip:true`. Reparent the already-built content frames into it and delete the standalone frame they came from, so the document holds one copy of each screen.

`design.md`'s Mocks section lists the screens the file holds: add the new pair there in the same pass, then read the edited range back — a `PUT` that repeats a line duplicates the paragraph while the edit still reports success.

## Agent panels beside a canvas

A prompt box parked in a corner is the surface the reference products rejected: tldraw's agent starter kit and Figma Make both dock a chat rail beside the workspace, with history and context attachments in it. Draw the rail, not a pill. Rail = 340 px `#171717` with a 1 px `#3B3B3B` left edge, header (title, session name, status dot, collapse chevron), a `clip:true` feed whose last message sits just above the composer, and a composer card `#1B1B1B` / 1 px `#3B3B3B` / radius 12 holding a context chip and a 28 px brand send. Collapsed state is a 48 px slim rail with a status dot and an expand chevron; on a phone the same rail is a bottom sheet with a grab handle, header and composer, over the canvas.

## Product-shot compositions

When the ask is a design, hero or feature-card shot rather than a screen to build, compose to the stageshow skill at `.agents/skills/stageshow` (`references/craft.md`, `references/framing.md`): one hero object, cropped 10-40% off stage and running off an edge, one gutter size on the other edges, at most one satellite straddling an edge or an annotation tied back with a leader, and 3-7 real strings. Build the crop as a stage frame with `clip:true` and a `cornerRadius`, `node.reparent` the finished screen into it, then `node.set` a position that overflows the stage; never shrink the screen to fit the stage. Crop through filler (a list may run one line off a bled edge), never through a control's label or a button. Duplicate finished screens with `edit.duplicate {ids, dx, dy, map:true}` and re-read the copy's tree by name to recover ids instead of redrawing them.

## Reusable components

When the ask is a components page, or a control that the app will reuse, build real components instead of copies of a frame:

1. Create the master with `node.create {type:"component", …}`, passing explicit `width`/`height` and `sizingH:"fixed"`, `sizingV:"fixed"`: a master inherits the parent's layout box otherwise, and every instance is born the wrong size.
2. Two states of one control are variants of one set: name the mains `<Set>/<Property>=<Value>` (`Tab/State=Active`) before `component.combineVariants {ids}`, which answers the set id. `instance.create {component:<set>}` gives the default variant; `instance.setProperties {properties:{"Tab/State":"Active"}}` switches one (an unknown property error names the real property).
3. A compound master (`Tabs`) that holds instances of the set makes the composition reusable too.
4. Show the linkage on the page with `instance.create`, and label the group `INSTANCES` so the reader sees they follow the masters.
5. Once a components page exists, every mock that shows that control carries an INSTANCE of it, never a hand-built copy of the treatment — a rebuilt underline tab row next to the real `Tabs` component is exactly what the user rejects. Place the instance, set `width`/`height` on it AND on each nested tab instance (children keep their master width when the instance is resized), then override the label with `node.set {id:<nested Label text id>, characters:"…"}` — instance descendants accept `characters`. Re-read the label width after the override and set the underline width to it, then `instance.setProperties` the active variant. An auto-layout parent with `sizingV:"hug"` regrows by itself when the instance is taller than the control it replaced; do not hand-fix the frame height.

`references/components.md` holds the recipe, the set-geometry trap and the specimen-page layout.

## Auto layout

- Every frame is created with FigCraft's default WHITE fill, so a container that should be transparent or inherit the parent's surface paints white over it: `node.set {fill:"none"}` on each wrapper, or give it the real token colour. This is the first suspect when an export shows white where the root's dark fill should show.
- `crossAlign:"center"` centres inside the frame's PADDING box, not the frame: a header padded `[0,0,12,0]` for a hairline centres a 20 px title in the 24 px that remains, 2 px off. Pad symmetrically (`[6,0,6,0]`) and let the border sit on a wrapper.
- `sizingV:"fill"` fills the parent's content box, and `strokesIncluded:true` takes the inside border out of it: a 42 px tab strip with a 1 px bottom border leaves 41 px tabs and a 1 px seam under the active underline. Set `strokesIncluded:false` on the strip and `mainAlign:"spaceBetween"` on the tab so the underline lands on the divider row.
- Pinned chrome comes from one `fill` child, not from pinning edges: give the root a fixed `height`, then the scrolling region `sizingV:"fill"` + `clip:true` between the fixed rows above and below it. The fill child absorbs the leftover, so a long list clips inside its own box while the search field, footer and any control under the list stay put. Land the clip mid-row — a 2-4 px sliver reads as a bug, not as more content — and add a 3 px `#525252` thumb with `props:{absolute:true, cornerRadius:1.5}` so a static mock shows the list scrolls.
- A created child's `x`/`y` are parent-relative, so page coordinates land at `parent + value`; convert before the call, and verify with `absoluteBounds`.
- `node.reparent` accepts only `{ids, parent, index}` (`unknown parameters \`x\`, \`y\``): reparent, then `node.set` the position.
- `references/auto-layout.md` holds the remaining engine quirks (batch `$ref` shape, duplicate maps, hugging frames shrinking) and the sampling recipe for a bled composition.

## Procedure

1. Do every FigCraft edit through the native `figcraft.*` MCP tools inside `execute` (`tools.call("figcraft.get_node", …)`, `tools.call("figcraft.batch", …)`, and `tools.call("figcraft.run_command", command:<cmd>, params:{…})` for every command): they attach to the live document by themselves, so there is no join, no driver and no wait. Saving and exporting are commands, not tools — `file.save {path}` and `file.export {ids, format, path, scale}` through `run_command`; `figcraft.save_file` and `figcraft.export` do not exist. A page is `page.add {name}`. Never write a build or driver script, never shell out to `figcraft-cli`, and never hand-roll a stdio JSON-RPC client — one `execute` per step is the workflow the user asked for.
2. `references/live-edit-session.md` keeps the stdio driver only for a host that has no `figcraft.*` tools at all; while those tools answer, do not open it.
3. Build with `run_command` steps and read every returned id. Created and imported nodes report `{id}`; `node.get {id}` reports `absoluteBounds` for the frame and each child, which is the geometry ground truth.
4. Take glyphs from the packages the app actually uses instead of retyping paths: lucide node data is `__iconData` inside `web/node_modules/@lucide/svelte/dist/icons/<name>.svelte`; brand logos are real files at `web/node_modules/@lobehub/icons-static-svg/icons/<id>.svg` (imported as `?raw` by `web/src/lib/brands.ts`). Write the svg with `width`/`height` at the rendered size, keep its `viewBox`, then `file.import {path,x,y}` in page coordinates and `node.reparent {ids,parent}`. Size every glyph to the app's 16 px icon box; `references/icons.md` has the node-data-to-path conversion, the wrapper recipe and the size check.
5. Verify the render, not the node report: `run_command file.export {ids:[one frame], format:"png", scale:1, path:"/tmp/x.png"}` and decode it with `zlib` + `struct` (no PIL). Export ONE frame per call: a multi-frame export pads, offsets and can reorder the frames, while a single-frame image maps pixel = frame-local coordinate * scale. Sample in frame-local coordinates and assert `0 <= x < width` and `0 <= y < height`: a negative index wraps to the opposite edge and returns a plausible colour from the wrong row. Assert fills, ink colours, right edges and the frame border; a glance at the image is not verification. The target directory must already exist (`<project>/.tmp/shots/`): `export` writes the file but never creates the folder.
6. Name layers with `node.set {id,name}` so the file reads like the screen (Placeholder, Mic, Send arrow), and finish with `run_command file.save {path: <project>/design.figcraft}`.

## Pitfalls

- `vector.create` with both `width` and `height` scales the path bbox non-uniformly: a 24x16.48 logo becomes a distorted 16x16 box. Width alone keeps the proportion, but some glyphs then come back at FigCraft's own aspect (an `x` measured 16x26.67), so set both dimensions explicitly for square icons and re-centre from `node.get` bounds.
- `file.import` can answer with an empty result and create nothing; when `node.get` on the answer finds no node, do not retry the import. Build the glyph with `node.create {type:"vector", path:<the __iconData path d>, props:{fill:"none", stroke:<token>, strokeWeight:1.33, strokeCap:"round", strokeJoin:"round"}}` and place it from its bounds.
- `node.set {path}` fits the vector layer to the path's own bbox in path units, so a 24-grid lucide glyph lands about 24 px wide and every icon comes back a different size. Leave the path as authored and wrap it in a fixed `16x16` frame (`fill:"none"`, `layout:null`, `clip:false`) created at the icon's own parent and index, reparent the vector in, then set `w,h = bbox*16/24` and centre it. `references/icons.md` covers the conversion, the multi-`<path>` concatenation trap and the size check.
- `collab.peers` is unreliable in both directions: it reports `status: "connecting"` with an empty peers list while edits land fine, and a session that has not attached still answers `node.create` with an id while writing a local copy. Probe readiness with a read (`node.get` on an existing id), never with the peers status or a create.
- Creation commands are commands, not MCP tools: `instance.create {component, x, y, parent}` runs through `run_command {command:"instance.create", params:{…}}` (calling it as a tool name fails with ``unknown tool `instance.create` ``), deleting layers is `edit.delete {ids}` (``unknown command `node.delete` ``), and `list_commands {filter:"instance"}` names the rest.
- `node.create` takes `padding` as a number or `[t,r,b,l]` and `strokeSides` as `[t,r,b,l]`: an object padding fails with ``invalid parameters for `node.create`: padding: n or [t,r,b,l]`` and `["l"]` fails with ``invalid parameters for `node.create`: strokeSides: [t,r,b,l]``. For a one-edge border draw a 1 px rectangle child on that edge instead of guessing the side syntax.
- A `parent` that resolved to nothing does not error: the node lands at page root in page coordinates, then clips away when reparented under a `clip:true` frame. Assert every id loaded from `tools.store` before a create, and re-read the parent's `children` right after — a node missing from that list was created elsewhere.
- A `fill`-sized master component bakes its parent's content box into the component: a 263x42 tab created inside a padded card came back 256x40 and every instance inherited that. Set the master's size explicitly with `fixed` sizing, and only use `fill` on instances.
- Restack a mock that already exists instead of deleting and redrawing it: `node.set {id, x, y, width, height, characters, cornerRadius}` moves and retypes the layers in place, so ids, fonts and colours survive and only the layout changes.
- After `save_file`, wait past the 5-second snapshot and re-stat the file, then re-read the frame's children: the daemon can write its own copy over yours, and a byte count that changed back is the only warning you get.
- `figcraft-cli run` cannot join a live session (`live sessions aren't available here`); only the MCP server hosts and joins them, and the `figcraft.*` tools inside `execute` already go through it. Do not reach for `figcraft-cli` or a driver script while those tools answer.
- `node.find {name: ...}` can answer with an empty list for imported frames. Keep the ids from each step's result and address nodes by id.
- A joined session starts from the live document, so ids are not the ones a local file used. Read ids from results; never hardcode them across sessions.
- A reparent can be missing after a later save (the child reappears page-level). Re-read the parent's children with `node.get` before the final `save_file`.
- A locked layer refuses every edit, including yours: `object.toggleLock {ids, locked:false}` (or `node.set {locked:false}`) before the next change, and say so when you lock a frame the user asked to protect. A lock applies to the whole subtree, so count the descendants (`get_node` depth) rather than the roots when reporting what was protected.
- `--scale 2` doubles every coordinate: sample pixels at `x*2, y*2`, and handle PNG filter types 1-4 when decoding, or rows shift and colours read wrong.
- A text node's measured height is not its line box: 13 px text can report 32 px tall while 12 px text reports 15. Place text by its top `y` and never vertically centre it from the returned height. A multi-line node does honour `lineHeight` when it draws (12 px at 160 % = 19.2 px pitch), so align an active-line highlight band to ink row groups in the export, not to the reported box, or the band sits a line off. `node.set {textAlign:"right"}` works for a line-number gutter.
- Measure the app's values from the component and `web/src/app.css` (box sizes, gaps, token colours) instead of guessing from the render; a composer row is padding + text + button height, not a round number.
- `node.set` rejects `parent` (`unknown properties: parent`): create, `node.set` the position, then `node.reparent {ids, parent}`. A `$ref` in `batch` is the object `{"$ref": "stepName"}`, not the string `"$stepName"` (a string fails with `` `parent` must be a node id (got "$card") ``), and it resolves only to a step of that same call, so a ref reused in a later `batch` fails with `names no step`.
- A `clip:true` frame hides any child placed outside its box: a 1 px divider created in a 30 px tab frame at `y:64` never draws. Put the hairline on the outer frame, or use parent-local `y`.
- Layers draw in creation order: a full-width hairline created last covers the bottom row of a tab underline. Move it down with `node.reorder {id, index:1}` or `arrange.back {ids}` and re-sample the underline pixels.
- A 1 px-high rectangle can vanish in a scale-2 export while drawing correctly at scale 1. Verify hairlines at scale 1 and trust the document, not that render.
- `textAutoResize:"widthAndHeight"` hugs and ignores `width`, so centred text needs `textAutoResize:"none"` plus an explicit width. Inter has no Medium (`Inter has no 'Medium' style` warning, drawn as Regular): use Regular and Semi Bold, and re-read the width after switching to Semi Bold before centring a label and its underline on the same axis.
- Re-read the root's `layout.gap` after a batch instead of trusting the reported positions: a gap that silently dropped to 0 makes a hug panel fit the fixed root exactly, so every child looks plausible while the `fill` region is the wrong height. Leftover `fill` height is computed after the gaps.
- Never conclude a subtree is unpainted from one pixel column: glyphs are sparse and a column between them reads as background. Export that frame alone and list the y-ranges holding any non-background pixel. A `fill:"none"` frame exports transparent (decodes as `#000000`), so sample colours from the filled parent's export, not the transparent child's.
- A hugging text wider than its card does not wrap and does not grow the card: it overflows the card's padding box and exports past the border. Set the text `width` to the card's content width (frame width minus both paddings) so long lines wrap, and let the card's `sizingV:"hug"` regrow from the wrapped height.
- `width` on a text node is its box, not its ink. Verify alignment with an ink bounding box (non-background pixels inside the box): it catches a clipped description, ragged right-aligned columns, and a suffix sitting on top of its value.
- After moving a block inside a feed or card, ink-scan the vertical gap down to the next fixed element (composer, footer, divider): a block whose ink ends exactly on that edge has zero spacing while its node box claims it fits.

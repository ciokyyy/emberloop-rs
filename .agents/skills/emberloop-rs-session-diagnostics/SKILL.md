# Session diagnostics

Answer "is this real or an error?" from the daemon's own records, never from the rendered page alone.

## Procedure
1. Get the URL the user pasted. The web app is one shell: every route in `web/src/routes/p/[project]/s/[session]/` is a stub, and `web/src/routes/+layout.svelte` picks the component by `view`. Read the route's component (e.g. the cache page renders `web/src/lib/components/CacheView.svelte`) to learn the endpoint it calls.
2. Reach the daemon's REST API directly with curl. The host in the URL serves `/api` too, so a hosted Session is diagnosable without shell access to that machine:
   - `GET /api/sessions` — every Session with its `model` and `thoughtLevel`.
   - `GET /api/sessions/<id>/usage?limit=N` — one `UsageRecord` per model request, oldest first (default 200, max 1000).
   - `GET /api/sessions/<id>/history?limit=N` — the event log: `usage`, `compression`, `prompt`, `tool_started`/`tool_finished`, `status`, `todos`, `error`.
   - `GET /api/settings` — `proxy_compression`, `inject_nudge`, `max_context_limit`.
   - `GET /api/status/tokens?month=YYYY-MM` — fleet rows for one month (`availableMonths`, `rows[]` per model × harness × project with calls, input/cached/output totals and latency) plus a `summary` of totals, cache hit and latency.
   - `GET /api/providers/<provider>/usage` — subscription windows: `windows[]` of `{label, usedPercent, resetsAt}` (ISO date or epoch seconds). Per plan, never per model.
   On the daemon's own machine the same records are cheaper to aggregate: `/root/.local/share/emberloop-rs/sessions/<id>/` holds `events/*.jsonl` (the history stream), `meta.json`, `nudge.json`, `splices.jsonl` and `exec/*.py` (every `execute` script run in that Session). `emberloop-daemon digest --session <id>` prints one Session's prompts, steers and tool calls as Markdown, archived Sessions included. Parse the event files in `execute` and print a computed table; a long Session is more than a thousand `usage` rows and printing them buries the pattern.
   Event line shape: `{v, seq, sessionId, kind, at, data}`. `usage.data` has `inputTokens`, `cachedTokens`, `cacheCreationTokens`, `contextWindow` and `breakdown` (`system`, `toolDefinitions`, `toolCalls`, `toolResults`, `compression`, `conversation`). `compression.data` has `action`, `kind` (`first`, `compress`, `fold-miss`, `skill-review`, `decompress`, tier kinds), `tokens`, `sinceLast`. To judge a threshold across the fleet, loop all `sessions/*/` and report per Session: usage count, max and median `inputTokens`, max `breakdown.compression` (summary mass), and a count of `compression` kinds. Skip Sessions under about 100 usage rows.
3. Correlate by `seq`, not by wall clock: `usage` events carry `seq` matching `UsageRecord.seq`, and the `compression` events between them explain what changed in the prompt. Print the merged timeline (nudge/compress interleaved with usage input, cached, hit) — that pattern usually names the cause in one screen.
4. Confirm the mechanism in the crate that produced it (`crates/proxy/src/…`, `crates/api/src/usage.rs`) and `crates/*/AGENTS.md`, then answer with the cause and the concrete knob or code path, not with a restatement of the numbers.
5. Weigh the cost and the spread before proposing a fix: sum the input tokens of the cold rows, express them as a share of all input, and run the same totals over the neighbouring Sessions. Churn concentrated in one Session is a gate or guard defect; churn spread evenly across Sessions is a policy or threshold decision.

## Fleet and quota questions

Cost, subscription-allowance and model-tier questions ("how much usage do I have", "which model belongs in which tier") use the same records at fleet scope; follow `references/provider-quota-audit.md`. For skill questions (are skills read, useful or too coarse, did a retro help), follow `references/skill-usage-audit.md`.

## Pitfalls
- Never run `grep -r` or `find` from the repo root without excluding `target`, `node_modules`, `.git` and `.claude/worktrees`; the walk outlives the 120s `bash` timeout and the tool kills the process group. Use the `grep` tool or add `--exclude-dir` plus `timeout 20`.
- Questions about how billion-context itself works (tiers, thresholds, layout) are answered from its public paper at `github.com/ranxianglei/billion-context` (raw `paper/*.md`), not DeepWiki, which rate-limits with HTTP 429. Compare against our gate defaults in `crates/proxy/src/nudge.rs` (`FIRST_NUDGE_TOKENS`, `NUDGE_GROWTH_TOKENS`, `tier2_trigger`, `tier3_trigger`) before proposing new numbers.
- A metric the provider cannot report is displayed as zero, and zero is not a fault: check the wire parser (`crates/proxy/src/meter.rs`) before calling it one. Gemini hardcodes `cache_creation_tokens: 0`, so a permanent `Written 0` is expected on the Google wire.
- A prompt that goes `working` to `idle` in under a second with no assistant text and no `usage` event never reached a model. Provider errors are not in the event journal; read the harness session file under `pi-homes/<id>/.pi/agent/sessions/` and follow `references/stuck-turns.md`.
- A replaced provider key reaches a Session only when its harness spawns: the open harness keeps the key it copied into `.pi/agent/models.json`, so prompting right after editing `~/.config/emberloop-rs/keys.json` repeats the 401. Evict the handle first (idle reap at 10 minutes, or a daemon restart), then prompt; the stored `resumeToken` carries the conversation over.
- A harness row with `stopReason: error`, `errorMessage: error sending request for url (http://127.0.0.1:3000/proxy/...): operation timed out`, `durationMs` about 300000 and `totalTokens: 0` is the harness's own client timeout, not a proxy verdict: the proxy's `DEFAULT_ROUND_TIMEOUT` is 120 s and no `usage` row was billed. Replay the route once with the harness token before blaming credentials or the request body; a streaming 200 in about a second proves a stalled upstream that recovered, not a config fault. A one-rung subagent tier cannot escalate, and each submit nudge then waits the same timeout, so one stall costs that timeout several times over.
- A turn that ends with an `assistant_chunk` `Agent execution error: Harness process exited unexpectedly (WS close code 1011)` on an agy Session carries the harness stderr in that chunk. `MCP tool call to server "el" timed out after 3m0s` there means a blocking `el` tool call (`bash`, `background wait`, `execute`) ran 3 minutes and Antigravity killed its own process. Match the failed `tool_finished` events (status `failed`, output `Failure in MCP tool execution`) to their `timeout` argument; `ToolConfig::max_call_secs` (`EMBERLOOP_MAX_CALL_SECS`, 170 for agy) is the clamp.
- `Agent execution error: model output error: … stop reason` on every turn, with `toolCalls: 0` across the whole Session, is a tool-declaration fault, not a model fault. Check `breakdown.toolDefinitions` first: near zero (1 token) beside a small `system` means the proxy's role allowlist stripped every declaration in `crates/proxy/src/wire.rs`, so a goldfish, scout or reviewer Session runs with no tools at all. `wire.rs::tool_name` must strip every harness spelling before matching — `mcp__el__<tool>`, `mcp__el_<tool>`, agy's single-underscore `mcp_el_<tool>` and bare `el_<tool>` — because a missed spelling silently drops an allowed declaration or keeps a forbidden one. Re-derive the filter's normalisation whenever this symptom appears. Compare a sibling Session on the same model with a normal role: identical `toolDefinitions` there proves the request is fine and the filter is not. The harness-side retry loop and the names agy really declared are in agy's own store — see `references/stuck-turns.md`. A `usage` row describes the request that precedes that turn's calls, so its `toolCalls: 0` is normal on a healthy Session: judge declarations from `toolDefinitions` and from the tool events, and call a turn healthy when later `usage` rows show `toolCalls`/`toolResults` above zero, `tool_started`/`tool_finished` pairs name allowed tools, and `status` is `idle` with `stopReason: end_turn`.
- An `error` event `"stream was interrupted: upstream error: error decoding response body"` followed immediately by a `notice` `"Retrying (attempt …)"` and resumed chunks comes from `SseState::next_chunk` (`crates/proxy/src/server.rs`): `send_stream`/`read_body_with_replay` retry `is_truncated` (`is_decode() || is_body()`), whereas `next_chunk` calls `publish_error` and terminates the SSE stream on the first chunk error even when the harness (`pi-rs`) retries and recovers. Check whether chunks resume after the notice before treating it as a lost turn.
- A tool that behaves differently inside `execute` than when called directly points at a branch that lives only in `crates/tools/src/mcp.rs` (`read` builds an image content block there) and not in `Toolbox::dispatch_inner`, which the execute bridge calls with a string-only reply. Reproduce both paths before blaming the file: call the tool directly, then `tools.read(...)` on the same path from a script.
- Empty `tools.search('graph')` or `tools.servers()` output inside `execute` does not mean `skill.codebase-memory` missed the frozen system prompt: `codegraph::ensure` (`crates/daemon/src/codegraph.rs`) sets `ProxyConfig::codebase_memory` synchronously at `Daemon::open` from `<config_root>/mcp.json`, whereas `execute` (`Toolbox::mcp_tools_soon` in `crates/tools/src/lib.rs`) caps `McpRegistry::tools()` at 1500 ms across all enabled servers sequentially, leaving `_MCP` empty on cold start while `tools.call('graph.<tool>', ...)` still connects lazily via `McpRegistry::attempt`. Check `<config_root>/mcp.json` validity and `graph.enabled` when the prompt itself is absent (outside `goldfish` isolation). To verify whether Sessions actually invoke an `execute`-only MCP server, scan `sessions/*/exec/*.py` for `<server>.` calls and `tools.search`/`tools.servers` instead of `events/*.jsonl` (which false-matches file paths and prose), and check `<config_root>/code-index/emberloop-setup.json` to see whether `codebase-memory-mcp` setup completed.
- To resume a Session that ended on `Agent execution error`, find it by scanning `sessions/*/meta.json` (a reviewer has a `reviewer` object with `parentId` and `role`) for a last `assistant_chunk` containing that string, then `POST /api/sessions/<id>/prompt` with `{"text": ...}`. `spawn`/`steer` reach only reviewers you spawned, so a reviewer under another parent needs the REST prompt. Say in the text what failed and what changed (for example the call cap), tell it to resume and `submit`, then check `/history?limit=6` a minute later for new `tool_started` events.
- Name the hop before theorising: `invalid request body:` is the proxy, `{"error":{"message":...}}` is structured backend validation, `{"detail":"..."}` is the backend's terse rejection, `Provider HTTP 5xx:` is the proxy wrapping an upstream failure. A bare `{"detail":"Bad Request"}` carries no cause.
- Fetch with `curl -o /tmp/<name>.json` and parse the file in `execute`. Piping curl into `python3 -c` is refused, and large JSON printed through `bash` spills to a `ctx:` handle before you can parse it. Read a journal with plain `open()` inside the script: `tools.bash("cat <path>")` answers a numbered, tagged view, so `json.loads` on that text fails.
- The cache page refetches whenever Session status changes; a UI that looks like it reloads is not evidence of a backend problem. Only the records settle it.
- Cache hit rate falling is real invalidation whenever the prompt prefix changed. Find the event that changed it (a fold, a steer, a model or wire switch) before blaming the meter or the UI; `UsageRecord.fold: true` names the fold on the row itself. See `references/prompt-cache.md`.
- A repeatedly re-firing nudge is a gate-state question, not a provider quirk: read the gate (`crates/proxy/src/nudge.rs`) and the `sinceLast`/`kind` fields on the `compression` events before theorising about caching.
- A golden or parity fixture taken from the reference implementation can encode the defect you are fixing. When its expected early nudge exists only because a fold reopened the gate, changing the golden is the fix; record the deliberate deviation in the fixture's doc comment so the next reader does not restore it.
- Fold-quality suspicions (model misreads the user's last message, summaries decay): read `<session>/spill/blocks/b*.json` (`start`, `originals`, `summary`). Every block with `start` 1 whose originals hold a prior summary turn means folds re-summarise blocks (`foldable_runs` in `crates/proxy/src/compressor.rs` treats summary turns as foldable, so nudge ranges always begin at 1). Blocks cover only raw turns added after the last block (the billion-context design: one non-compounding fold per increment, tiering only as a deliberate step). `foldable_runs` therefore ends a run at a summary turn, and `refuse_block_folds` in `server.rs` rejects a model `compress` range that includes one; `compress_batch` itself stays permissive so legacy nested blocks still replay. Summary turns also carry the `user` role, so the model can read its own handoff text as user speech. Read `start` as a turn index only after scanning `originals` for summary text: successive blocks starting at 1, 2, 3 … are the normal non-compounding case, because each `start` counts the summary turns already ahead of it. A summary that quotes the user's numbered answers verbatim while only naming the agent's "N-question list" has dropped the questions themselves, so the next numbered answer cannot be mapped and the model says it cannot see the list.
- A `compress` the daemon refuses is a guard answering, not a bug: the message names which one. `refuse_cache_costly_folds` (`crates/proxy/src/server.rs`) rejects a fold that frees less than a quarter of the tokens it rewrites once the rewritten tail passes 20000; `refuse_block_folds` rejects a range that contains a summary turn. Ranges are indices into the CURRENT `contents`, which renumbers when a fold lands, so a stale `end` resolves to an empty range and reports `fold frees about 0 tokens but rewrites N`. Read `acp_status` for the live bounds and fold a later range that holds real mass instead of retrying the same numbers.
- Search agent text only after concatenating a whole turn: `assistant_chunk` rows are token fragments, so a line-wise regex over the journal finds zero hits for a phrase that is really there. Group chunks between `prompt` rows, join them, then search.
- Tool output inside an `execute` script must arrive whole: `Toolbox::maybe_spill` skips spilling while the `IN_SCRIPT` task-local is set (scoped around `call_inner` in `crates/tools/src/execute.rs`). Only the script's final printed output spills at 10 KB, so a script filters before printing instead of paging a `ctx:` stub. When `ctx_spill_enabled` is false (in Settings, default false), both tool-level overflow spilling and proxy CCR placeholder replacement are paused completely; reads of existing historical `ctx:` handles remain functional.
- Agy (Antigravity ACP) tool runs showing summary/action text instead of actual output/diff: Antigravity passes the model's `toolAction`/`toolSummary` in `call.title` and `ToolCallContent` (`call.content`), while actual tool execution results/diffs land in `raw_output`. In `crates/harness-acp/src/lib.rs`, `tool_output` must prioritize valid `raw_output` over `content`, otherwise summary strings displace real stdout and diff outputs. Route `call.title` / `content` texts into `title`/`summary` on `ToolStarted` and `ToolFinished` so the UI (`web/src/lib/feed.ts` and `ToolFeed.svelte`) can display them as running status or tool subtitles without clobbering tool output.
- In diagnosing cascading tool spills or repetitive `read ctx:` traps: look for recursive spills where output paging a `ctx:` handle itself exceeds 10 KB and mints a child handle, or an execute script that calls `tools.read` on a spill handle and re-emits it. Check whether `ctx_spill_enabled` is active and inspect `sessions/<id>/spill/` count vs actual `read ctx:` / `ctx_search` usages.
- Tool-usage questions ("is tool X used or needed?"): `tool_started` events with an empty `name` are streaming updates (about 94% of rows), so count only rows with a name, preserve the first non-empty name when aggregating by call `id` (never let an empty-name chunk overwrite a real name), and normalize `mcp__el__`/`mcp__el_`/`mcp_el_`/`el_` prefixes (`todo` covers `mcp__el__todo`, `mcp_el_todo` and `el_todo`). A `todos` event is a state snapshot re-emitted at turn end, not a call, so its last row always sits at the final request; count `tool_started` calls instead, and join `tool_finished` by `id` for the `failed` share. Report calls as a share of all named calls, plus how many long Sessions made zero calls.
- The harness answering `Tool <name> not found` for a proxy-only tool (`compress`, `decompress`, `search_context`, `acp_status`) means the proxy forwarded that completion's stream to the harness. Note the absence of a harness `tool_finished` for the call id: the harness ran it locally from the forwarded `tool_calls` chunks, so only pi's session file records the failure. Decide it from pi's assistant record for that round: a forwarded round carries its own `responseId` and `usage`, whereas a proxy follow-up round would carry a different `responseId`. Mechanism in `crates/proxy/src/server.rs` `decide_stream_calls`: any buffered `StreamCall` whose name is not in `PROXY_TOOLS` makes the whole stream a harness stream, so a nameless fragment from a gateway (`{"index":1,"function":{"arguments":""}}`, or a blank `function.name` delta) is enough to forward everything; a nameless call never counts as harness work, and `collect_openai_call` must not let an empty name overwrite a real one.
- A Session page that renders empty until a reload after switching Sessions is a reconnect race in `web/src/routes/+layout.svelte`, not a missing stream: the `stream.onerror` retry timer outlives the selection and calls `openStream(oldId)`, whose `closeStream()` kills the current Session's stream, and the `apply()` snapshot handlers then drop the old Session's events. `openStream` must return early when `selected !== id`, before it closes anything. The race is likely on a daemon update, when every open EventSource errors at once; a throttled tab switching fast only looks the same if it recovers within a second.
- A Session that compresses over and over without its context shrinking (17 near-identical `compress` calls, input tokens flat or rising, nudge re-firing) is a fold that never applies, not a slow agent. List the `compression` events: a `fold-miss` right after every `compress` names the block, the turn that differs and both turn shapes. Compare `spill/blocks/b*.json` `originals` against that line. A stored turn that is one `functionResponse` where the request holds several in one turn means the stored block and the request disagree on parallel-result shape (chat wires: one turn per result; Anthropic wire and `carry::sanitize` merge them). `compressor::find_wanted` retries with the stored results merged; other shape differences (text, names) are not tolerated, so extend that normalisation, never loosen `same_turn`. Until a fixed daemon is deployed, steer the agent not to call `compress` again: every further call is a no-op that repeats the same range.
- Judge a rendered page by `document.querySelector('main').innerText.length`, not by mounted feed rows: a Session with tens of thousands of events legitimately shows zero rows for several seconds while the virtualizer fills.
- An ignored nudge is silent for the next `NUDGE_GROWTH_TOKENS` (50k): `observe_with` sets `last_nudge_tokens` on every nudge, answered or not. To measure agent lag, count `usage` rows from each `first` nudge to the next `compress` action; lags of 30 to 90 requests mean the gate is quiet, not the agent slow.
- A threshold that traces to a spec or parity constant is the user's decision, not part of the diagnosis: measure what it costs (the context and hit rate the Session reached while ignoring a nudge), state the one-line change, and leave the constant alone until they say yes.

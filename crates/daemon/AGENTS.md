# AGENTS.md — crates/daemon

## Reviewer subagents

Runner and manual harness wiring pass `EMBERLOOP_SESSION_URL` and `EMBERLOOP_REVIEWER`; stdio MCP reads them into `ToolConfig`. The API error watcher starts after the event persister. Startup recovers report delivery after binding the listener. See Versioning and update for continuation rules.


## Purpose

Composition root and binary for the whole system.

FigCraft uses matching upstream 0.16.0 native binaries and web assets installed by `scripts/install-figcraft` (Linux x86_64/aarch64; no container). `figcraft.rs` registers project-live metadata/server paths in `mcp.json`; `serve` owns a loopback `figcraft-server` child at port 47900 with durable state under `<config root>/figcraft/server`. `/figcraft/` serves the unmodified upstream web release from `/usr/local/share/figcraft`. The native server is separate from the browser editor; the API proxies its live connection. If installation or startup fails, chat stays available and the design endpoint reports unavailable.
- `Config` and `Cli` (clap) carry `--port` (3000), `--host` (127.0.0.1), `--data-root` (default `~/.local/share/emberloop-rs`), `--config-root` (default `~/.config/emberloop-rs`), `--upstream`, and `--allow-remote`. A non-loopback host is rejected without `--allow-remote`; the accepted bind logs a warning. The default root is ours, not the Go Emberloop's `~/.local/share/emberloop`; harness binaries live under the data root (`pi/v0.12.11/pi`, `agy-acp/1.4.5/…`), so an install that moves the root must symlink or copy them there or a spawn fails with `No such file or directory`.
- `Daemon::open` loads `DataRoot`, `ProjectsStore`, `SessionsStore`, a `PromptStore` rooted at `<config root>/prompts`, starts the prompt watcher and calls `codegraph::ensure`, whose answer gates the proxy's codebase-memory skill. The proxy and API share one `EventBus` and one `Settings` lock, so a Settings save reaches the next proxy request; the API gets the config-root prompt store through `AppState::with_prompts`, and `Daemon::open` starts the model catalogue refresher at boot.
- `router` merges the REST/OpenAPI router and the proxy router, then serves `web/build` through `rust-embed`. Unknown `/api` paths stay 404; every other path falls back to `index.html`, so an app deep link such as `/p/<project>/s/<session>` survives a refresh. `rust-embed` bakes `web/build/` at compile time and git ignores it, so a release build runs `(cd web && bun run build)` first; `tests/web_bundle.rs` fails when the bundle is older than `web/src`, which is how a stale UI cannot ship.
- `toolbox_for` and `mcp_server_for` build a Session's tools from its Project root and spill dir. `run_mcp` serves those tools over MCP stdio for the `mcp` subcommand, which `harness_wiring` puts in `HarnessWiring.mcp_command` along with a signed `/proxy/<token>` proxy URL. Both pass `ToolConfig::mcp_file = <config root>/mcp.json`, so a Session's `execute` can reach any stdio MCP server the file lists.
- `Config::global_skills` (default `$HOME/.agents/skills` of the daemon process, `default_global_skills`) is the global skills root. `harness_wiring` and `SessionRunner::wiring` pass it to the MCP subcommand as `--global-skills`, and `toolbox_for` gives it to the in-process toolbox. `run_mcp` takes it as an argument; `mcp_tool_config` builds the MCP process's `ToolConfig`, since a Session's MCP process has a pi-home `HOME`. It also reads `EMBERLOOP_MAX_CALL_SECS` (set by the Antigravity harness) into `ToolConfig::max_call_secs`.
- `codegraph.rs` owns the `graph` entry in that file: `ensure` writes `mcpServers.graph` (codebase-memory-mcp, `codebase-memory-mcp` from PATH or `npx -y codebase-memory-mcp@0.12.1`, cache under `<config root>/code-index`, the five exploration tools, and `setup` commands that turn on auto index, auto watch and ignore-worktrees) only when the key is absent, so a hand-edited entry always wins; broken JSON is left alone. It spawns nothing: the tools crate connects lazily, and the setup commands run once per connect.
- `review.rs` holds `ReviewExecutor`, the `proxy::ReviewTools` the daemon injects into `ProxyConfig` (see the proxy's background skill review). It allows only `skill_manage`, `skill_search`, `prompt_propose`, `read`, `grep` and `find` (by short tool name), denies the rest with a fixed message, and builds a `Toolbox` for the Session per call, with `prompts_dir` set to `<config root>/prompts` so `prompt_propose` stages a proposal and never changes a prompt. `SessionRunner::freeze_catalog` writes `<session>/skill-catalog.md` once, before the harness spawns (intro from the `skill.catalog` prompt, lines from `tools::skills::catalog`); the file is never rewritten, so a skill made later reaches the next Session.
- `HarnessPlugin` wires both `AgyHarness` (`EMBERLOOP_AGY_BIN` or `<data root>/agy-acp/1.4.5/agy_acp_server.par`) and `PiHarness` (`EMBERLOOP_PI_BIN` or `<data root>/pi/v0.12.11/pi`), routing `opencode-go/*`, `openai-codex/*` and registry-provider models (`emberloop_core::providers`) to `PiHarness` and others to `AgyHarness`; `PiSource` feeds pi’s offline RPC metadata (per-model efforts, image support and context windows) into `ModelCatalogue`, the pi HOME rewrites signed OAuth endpoints and pins full-context SSE on each connect, and `AgyLogin::with_keys` manages `<config root>/keys.json` (`providers()` lists every registry provider with `auth: key`).
- `serve` binds the configured host, serves until SIGINT or SIGTERM, and the watcher stops when the daemon drops.

Each Session's harness handle lives in `SessionRunner.handles` only while it is usable. The pump removes its handle when its event stream ends, and a failed `send`/`wake` evicts it; the next message then spawns a new harness and resumes the stored token. Every removal goes through `retire`, which stops the pump and awaits `HarnessSession::close`, so no child is left unwaited.

The idle reaper (`idle.rs`, `SessionRunner::reap_idle`, `watch_idle` every 30 s) closes a Session's harness and tool server once it has no running turn, no pending steer, no live background job (`tools::background::any_running`) and has been quiet for `Config.idle_timeout` (`--idle-timeout-minutes`, default 10). Quiet time counts from the last use or turn end. The clock is injected (`Clock`, `ManualClock` in tests), so tests never sleep.

Model settings go through `SessionRunner::configure_model`: working turns are refused, a harness-family change requires a new Session, and a live same-harness change awaits ACP acknowledgment. A refusal attempts to restore the prior model/effort and leaves API metadata unchanged. A Session not yet connected uses the saved settings on its next spawn.

## Versioning and update

`update.rs` owns `VERSION`, `compare`/`is_newer`, the release manifest `Latest { version, targets: { <triple>: { url, sha256 } } }`, `fetch` (URL from `EMBERLOOP_UPDATE_URL` or the GitHub release `latest.json`), with every download (manifest and artifact) retried through `gh release download` (`EMBERLOOP_GH` overrides the binary) when plain HTTP to a `github.com` release URL fails, since some networks answer release downloads with 504; a queue write into a missing data root names that root and `--data-root` and the release store under `$EMBERLOOP_HOME` (default `~/.local/share/emberloop-rs`, so the Go Emberloop's `~/.local/share/emberloop` is never touched): `install` downloads, checks the sha256 and keeps `releases/<version>/emberloop-daemon`; `activate` switches the `current` symlink atomically; `link_launcher` makes `$EMBERLOOP_LAUNCHER` (default `~/.local/bin/emberloop-daemon`) follow `current`; `prune` keeps the newest 3 plus current and its predecessor; `rollback` re-points `current` at the release before it. The running binary is never overwritten. `emberloop update [--manifest URL] [--session ID] [--check] [--rollback] [--file PATH] [--major]` (`UpdateRequest`, `run_update`) never installs itself, in a Session or out of one: it writes `update-request.json` (`InstallRequest`) to the daemon's data root (a Session's bash tool exports `EMBERLOOP_SESSION_DIR` = `<data root>/sessions/<id>`, and the report tells the model to end its turn). The runner's `watch_updates` task (every 2 s and once at start) and every turn end run `apply_pending_update`. The updater waits for the requesting Session to be idle, or all Sessions when no requester is named. It records other active Session IDs in `PendingUpdate.also`, runs `apply_request` (install, activate, prune, marker), relinks the launcher and `reexec`s `current` with the same arguments. The new daemon's `announce_update` appends one `EventKind::Notice` to that Session and `serve` re-prompts it through `SessionRunner::wake` once the listener is up; the harness `resume_token` carries the conversation. Every other active Session in the marker, including both reviewer roles, receives `continue` through the same wake path. Other idle Sessions are not resumed; stop, failure, and unplanned restart do not trigger automatic review retries. A failed apply is reported once as an `Error` event on the Session that went idle. Harness child processes of the old daemon are not stopped by the restart. `GET /api/version` in `crates/api` reports the same version. `--file` queues a binary already on this machine (a local build) the same way, and the release is named by the version the binary reports, so binary and release directory always agree: `build.rs` bakes `EMBERLOOP_BUILD_VERSION` (default: the crate version) and `binary_version` reads it back from `<binary> --version`. `--next-version` prints the version the next release would carry (`next_version` steps the last number, or the first with `--major`), and `scripts/release` uses it to build with that version and write the raw binary plus `latest.json` (`--publish` uploads them with `gh`); a queued path is made absolute when queued, because the installing daemon runs from its own working directory. A release directory of the same version is replaced.

After the queued restart, compare `current/emberloop-daemon --version`, `GET /api/version`, and the running service process executable. A queued request is not an installed release; a working requester delays it, or any working Session when no requester is named. Do not kill the daemon while a Session is working. Resume depends on the harness accepting its saved token: if loading fails, the runner starts a new harness conversation and resets proxy history, while the UI event log remains.

## Tests

Before it numbers a harness event the runner awaits `EventBus::settled` (250 ms cap), so the feed keeps provider order. `SessionRunner` stores the harness `resume_token` in `meta.json`, passes it back with the stable `<session>/agent-work` directory on the next spawn, resets the proxy history (splices, compressed blocks) when the harness conversation started over, enriches tool events with bash command classification (`display.kind`, `display.parts`) and write-tool unified diffs (`display.diff`) via `tooldisplay.rs`, and emits `EventKind::Status` (`{"state": "working"}`) on prompt and idle steer wakes, and publishes the stored plan as an `EventKind::Todos` event after each `todo` tool call and at every turn end. The runner publishes no `EventKind::Usage`; the proxy publishes one per request for every harness. The `TurnFinished` `usage` object stays in the idle status payload. At turn end `turn_end_todos` reads `<session>/todos.json` (the tool process owns it) and, when the Session is settled, enqueues one `SteerKind::Notice` before the idle wake so it merges with any queued steer; the reminder text is the `todo.reminder` prompt rendered from the Prompt Store (`ProxyState::prompts`), with the open items as the `open_todos` value; `crates/daemon/src/todo_reminder.rs` holds the pure rules (open set = pending or in_progress, at most `todo_reminders_max` per prompt cycle reset by the next user message, never the same open set twice). Settled means no steer queued and no background job running: the harness exposes no "question pending for the user" signal, so that part of the rule is the known gap. Once the cap is reached the runner publishes one `notice` event (`route: "cap"`) for the feed and sends nothing further. `tests/acceptance.rs` covers Ticket 11 checks 1, 2, 7, 8 against a fake upstream: Project/Session persistence, token rejection and acceptance, prompt pinning across a config edit, background PID adoption across a daemon restart, embedded SPA fallback, remote-bind validation, and harness wiring.

`tests/skill_roots.rs` checks that `mcp_tool_config` exposes the global skills root only when `--global-skills` is given. `tests/runner.rs` covers the frozen catalog (a skill made mid-Session stays out of that Session's file and appears in the next one). `review.rs` unit tests cover the whitelist denial and that `prompt_propose` passes it.

## Titles and provider usage

`titles.rs` uses the pinned pi-rust `pi-ai` SDK directly with no tools or harness process. It resolves saved keys and pi OAuth credentials, defaults to `openrouter/openrouter/free`, and retries generation or persistence indefinitely with 2–60 second backoff. Jobs are deduplicated per Session and stop on deletion, manual rename or disabled generation. Successful commits publish `session_title`; a failed title request never fails the chat turn. Pending jobs are process-local and start on a user prompt.

`usage.rs` reads ChatGPT subscription windows, Antigravity quota buckets, OpenCode Go windows, OpenRouter credits and DeepSeek balances. `AgyLogin` caches each provider response for 60 seconds; explicit refresh bypasses the cache. Credentials stay in the daemon. Antigravity exchanges its refresh token at the fixed Google token endpoint without writing credentials. Provider errors are redacted, JSON responses are capped at 1 MiB, and other cards remain available.

`pi-ai` is pinned to `ciokyyy/pi-rust` commit `0dd48c646cac3fc321151f7b474495630bfa53be`, based on upstream `v0.12.11`, with `ruzstd 0.9.1` and SDK Rust minimum 1.87. This fixes `RUSTSEC-2026-0344` without an advisory exemption. Switch back to an upstream release once it includes the dependency fix.

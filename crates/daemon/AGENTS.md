# AGENTS.md — crates/daemon

## Purpose

Composition root and binary for the whole system.
- `Config` and `Cli` (clap) carry `--port` (3000), `--host` (127.0.0.1), `--data-root` (default `~/.local/share/emberloop-rs`), `--config-root` (default `~/.config/emberloop-rs`), `--upstream`, and `--allow-remote`. A non-loopback host is rejected without `--allow-remote`; the accepted bind logs a warning. The default root is ours, not the Go Emberloop's `~/.local/share/emberloop`; harness binaries live under the data root (`pi/v0.12.11/pi`, `agy-acp/1.4.5/…`), so an install that moves the root must symlink or copy them there or a spawn fails with `No such file or directory`.
- `Daemon::open` loads `DataRoot`, `ProjectsStore`, `SessionsStore`, a `PromptStore` rooted at `<config root>/prompts`, and starts the prompt watcher. The proxy and API share one `EventBus` and one `Settings` lock, so a Settings save reaches the next proxy request; the API gets the config-root prompt store through `AppState::with_prompts`, and `Daemon::open` starts the model catalogue refresher at boot.
- `router` merges the REST/OpenAPI router and the proxy router, then serves `web/build` through `rust-embed`. Unknown `/api` paths stay 404; every other path falls back to `index.html`, so an app deep link such as `/p/<project>/s/<session>` survives a refresh.
- `toolbox_for` and `mcp_server_for` build a Session's tools from its Project root and spill dir. `run_mcp` serves those tools over MCP stdio for the `mcp` subcommand, which `harness_wiring` puts in `HarnessWiring.mcp_command` along with a signed `/proxy/<token>` proxy URL.
- `HarnessPlugin` wires both `AgyHarness` (`EMBERLOOP_AGY_BIN` or `<data root>/agy-acp/1.4.5/agy_acp_server.par`) and `PiHarness` (`EMBERLOOP_PI_BIN` or `<data root>/pi/v0.12.11/pi`), routing `opencode-go/*`, `openai-codex/*` and registry-provider models (`emberloop_core::providers`) to `PiHarness` and others to `AgyHarness`; `PiSource` feeds pi’s offline RPC metadata (per-model efforts, image support and context windows) into `ModelCatalogue`, the pi HOME rewrites signed OAuth endpoints and pins full-context SSE on each connect, and `AgyLogin::with_keys` manages `<config root>/keys.json` (`providers()` lists every registry provider with `auth: key`).
- `serve` binds the configured host, serves until SIGINT or SIGTERM, and the watcher stops when the daemon drops.

Model settings go through `SessionRunner::configure_model`: working turns are refused, a harness-family change requires a new Session, and a live same-harness change awaits ACP acknowledgment. A refusal attempts to restore the prior model/effort and leaves API metadata unchanged. A Session not yet connected uses the saved settings on its next spawn.

## Versioning and update

`update.rs` owns `VERSION`, `compare`/`is_newer`, the release manifest `Latest { version, targets: { <triple>: { url, sha256 } } }`, `fetch` (URL from `EMBERLOOP_UPDATE_URL` or the GitHub release `latest.json`) and the release store under `$EMBERLOOP_HOME` (default `~/.local/share/emberloop-rs`, so the Go Emberloop's `~/.local/share/emberloop` is never touched): `install` downloads, checks the sha256 and keeps `releases/<version>/emberloop-daemon`; `activate` switches the `current` symlink atomically; `link_launcher` makes `$EMBERLOOP_LAUNCHER` (default `~/.local/bin/emberloop-daemon`) follow `current`; `prune` keeps the newest 3 plus current and its predecessor; `rollback` re-points `current` at the release before it. The running binary is never overwritten. `emberloop update [--manifest URL] [--session ID] [--check] [--rollback]` (`UpdateRequest`, `run_update`) installs at once outside a Session and leaves the `PendingUpdate { from, to, session }` marker in `<data root>/update-pending.json`. Inside a Session (the bash tool exports `EMBERLOOP_SESSION_DIR` = `<data root>/sessions/<id>`) it installs nothing: it writes `update-request.json` (`InstallRequest`) and tells the model to end its turn. At every turn end `runner.rs` `apply_pending_update` checks for that request and, when no Session has a turn running, runs `apply_request` (install, activate, prune, marker), relinks the launcher and `reexec`s `current` with the same arguments. The new daemon's `announce_update` appends one `EventKind::Notice` to that Session and `serve` re-prompts it through `SessionRunner::wake` once the listener is up; the harness `resume_token` carries the conversation. A failed apply is reported once as an `Error` event on the Session that went idle. Harness child processes of the old daemon are not stopped by the restart. `GET /api/version` in `crates/api` reports the same version.

## Tests

`SessionRunner` stores the harness `resume_token` in `meta.json`, passes it back with the stable `<session>/agent-work` directory on the next spawn, resets the proxy history (splices, compressed blocks) when the harness conversation started over, enriches tool events with bash command classification (`display.kind`, `display.parts`) and write-tool unified diffs (`display.diff`) via `tooldisplay.rs`, and emits `EventKind::Status` (`{"state": "working"}`) on prompt and idle steer wakes, and publishes the stored plan as an `EventKind::Todos` event after each `todo` tool call and at every turn end. At turn end `turn_end_todos` reads `<session>/todos.json` (the tool process owns it) and, when the Session is settled, enqueues one `SteerKind::Notice` before the idle wake so it merges with any queued steer; `crates/daemon/src/todo_reminder.rs` holds the pure rules (open set = pending or in_progress, at most `todo_reminders_max` per prompt cycle reset by the next user message, never the same open set twice). Settled means no steer queued and no background job running: the harness exposes no "question pending for the user" signal, so that part of the rule is the known gap. Once the cap is reached the runner publishes one `notice` event (`route: "cap"`) for the feed and sends nothing further. `tests/acceptance.rs` covers Ticket 11 checks 1, 2, 7, 8 against a fake upstream: Project/Session persistence, token rejection and acceptance, prompt pinning across a config edit, background PID adoption across a daemon restart, embedded SPA fallback, remote-bind validation, and harness wiring.

## Titles and provider usage

`titles.rs` uses the pinned pi-rust `pi-ai` SDK directly with no tools or harness process. It resolves saved keys and pi OAuth credentials, defaults to `openrouter/openrouter/free`, and retries generation or persistence indefinitely with 2–60 second backoff. Jobs are deduplicated per Session and stop on deletion, manual rename or disabled generation. Successful commits publish `session_title`; a failed title request never fails the chat turn. Pending jobs are process-local and start on a user prompt.

`usage.rs` reads ChatGPT subscription windows, Antigravity quota buckets, OpenCode Go windows, OpenRouter credits and DeepSeek balances. `AgyLogin` caches each provider response for 60 seconds; explicit refresh bypasses the cache. Credentials stay in the daemon. Antigravity exchanges its refresh token at the fixed Google token endpoint without writing credentials. Provider errors are redacted, JSON responses are capped at 1 MiB, and other cards remain available.

`pi-ai` is pinned to `ciokyyy/pi-rust` commit `0dd48c646cac3fc321151f7b474495630bfa53be`, based on upstream `v0.12.11`, with `ruzstd 0.9.1` and SDK Rust minimum 1.87. This fixes `RUSTSEC-2026-0344` without an advisory exemption. Switch back to an upstream release once it includes the dependency fix.

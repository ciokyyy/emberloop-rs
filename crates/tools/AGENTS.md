# AGENTS.md — crates/tools

## Reviewer subagents

`subagents.rs` proxies `spawn`, `steer`, `stop`, `result` and `submit` to the current Session API when `ToolConfig.session_url` is set; `spawn` and `steer` expose optional `tier` (`smol`, `mid`, `top`) for `worker` and `scout`, and `spawn` takes `role=goldfish` with a required `persona` id (the Session API validates it and owns the one-shot rules; `goldfish` is not yet a distinct `SubagentKind`, so it currently falls into `Worker` here and the proxy allowlist enforces its read-only tools). `Toolbox::denied_reason` derives `SubagentKind` from `ToolConfig.subagent_role` (`EMBERLOOP_SUBAGENT_ROLE`, checked via `emberloop_core::steer::is_reviewer_role`) and `ToolConfig.reviewer`, gating both `tool_available` and `call_inner` identically: all subagents lose `spawn`, `steer`, `stop` and `result` while keeping `submit`; `spec`/`standards` lose `edit`; `scout` loses `edit` and `write`; `worker` retains both. For `scout`, `bash` enforces `intercept::scout_blocked` (single-pass tokenizer and fail-closed read-only command/flag allowlist covering direct and `execute`-bridged `bash` calls); `cargo check` remains allowlisted per spec despite executing `build.rs`/proc-macros, and other non-edit tools stay available (this is not a filesystem sandbox).


## Purpose

MCP tool server and tool implementations served to every harness over MCP.
`emberloop-mcp --root <project> --spill <spill dir>` serves rmcp over stdio;
`McpServer` implements `rmcp::ServerHandler` and is covered by tests. Descriptions
are the Prompt Store's `tool.<name>.description` texts: `McpServer::new` advertises
the embedded defaults and the daemon overrides them with `with_descriptions`. Input
schemas are inline in `mcp.rs`; `tests/contract.rs` checks each text against its
schema. Tools, path jail, spill store and seen-line store:

- `jail`: `resolve_any` and `resolve_writable` take any path the account can open: `~` expands from `HOME`, a relative path joins the Project root, the deepest existing ancestor is canonicalized so symlinks resolve. `read`, `edit`, `write` and `bash` views use them, because `bash` is no sandbox and a refused edit only pushes the model into the shell. `resolve` keeps `grep` and `find` inside the canonical Project root, symlinks included; `ProjectJail::with_extra_root` (set from `ToolConfig::global_skills`) also admits the canonical global skills root and the canonical target of each direct child of it, a symlinked skill, listed on every call.
- `read` goldfish jail: `Toolbox::resolve_read` sends a caller whose `ToolConfig.subagent_role` is `goldfish` through `ProjectJail::resolve_goldfish`, an allowlist: the Project root, the skill roots (global, plus project skills under the Project root) and the goldfish's own Session directory (`spill_dir`'s parent). Everything else is refused, including other Sessions, `claude-homes/<id>`, `pi-homes/<id>`, other Projects, `~/.ssh` and daemon settings; a symlink out of an allowed root resolves to its target and is refused. Other callers, scouts and workers included, keep `resolve_any`. A goldfish still reads `AGENTS.md` committed in the Project.
- `grep`: regex over `ignore`'s `.gitignore`-aware walk; content, files or count output.
- `find`: local lexical `search` (hits feed the seen-line store) and `outline`, plus `architecture` and unpathed `trace` through the `graph` MCP server when it is configured and healthy and the caller is not a goldfish. `direction` (`inbound`/`outbound`) and `depth` (1-5) steer `trace`; a pathed trace stays local. `McpRegistry::call_within` gives a cold connect 15s (capped by `cap_secs`) and the RPC 5s, leaving a timed-out connect warming in a tracked task. Any `Failed` (connect, unknown tool or RPC error) or post-connect timeout trips a 60s `Toolbox` cooldown; missing, cooling, goldfish, empty or truncated answers log `find.graph.fallback` and use `architecture_mode_local`/`trace_mode_local`. Graph results are `[graph]` JSON and neither they nor `outline` touch the seen-line store.
- `skillpath.rs`: the path grammar and the write rules of a skill, shared by `read`, `edit` and `write`. `parse` takes `el://skills/<root>/<name>/<rel>` with `<root>` `global` or `project` and `<rel>` defaulting to `SKILL.md`, `el://skills` for the index, and normalizes the `skills://` and `skill:` aliases; the short form `el://skills/<name>/<rel>` has no root. `resolve` returns both `path` (under the skill root as spelled, so `log_view`, `lock` and `backup` stay with that root) and `key` (canonical, the seen-store key), and the short form picks the project root first, then global. `display` renders the root-named path that replies and stale-tag errors show. `writable` is what `edit` and `write` call: `Some` for a root-named path, `None` for any other path, and a refusal naming `el://skills/global/<name>/...` and `el://skills/project/<name>/...` for the short form and every other skill URL, so a disk path inside a skill root keeps working with no skill rules. `check_write` holds the rules: a valid name, `global` and `project` reserved for a new skill, a name free in both roots, frontmatter `name` equal to the folder, a description of at most 1,024 characters, `SKILL.md` at most 100,000 characters, agent origin for an existing skill (a missing origin means `human`) and for the text that replaces it, supporting files only under `references/`, `templates/`, `scripts/` or `assets/` (at most 1 MiB) of a folder that already has a `SKILL.md`, and read-before-write. `commit` locks the skill, backs up the old bytes, writes, records the seen snapshot under `key` and appends the `.usage.jsonl` line (`create`, `patch` or `write_file`); a create inserts `metadata.origin: agent` when the frontmatter has none. One call changes one file: a skill that needs several writes goes `SKILL.md` last.
- `write`: a whole file, parent directories created. A skill path runs `skillpath` and prints its root-named header.
- `edit`: hashline grammar (`PUT N.=M:`, `PUT <N:`, `PUT >N:`, `PUT >$:`, `CUT N`, `CUT N.=M`), one-pass apply against original numbering, sha256 tag check, stale-tag rebase when changes miss anchored lines, anchors must have been shown by the tag's view. A skill path runs `skillpath::check_write` then `commit`, and keys the seen store by its canonical `key`.
- `websearch`: searches Brave and Exa APIs with freshness, domain filters, and 15-minute file cache; keys come from the tool-key file Settings writes (`ToolConfig::tool_keys_file`, read on every call), never from the environment.
- `execute`: runs `python3 -I` in its own process group with a generated `tools.py` Unix-socket bridge (`tools.parallel`, `tools.store`/`load`, `tools.save`/`run`, `tools.rerun`/`exec_source`, 500-call cap). A script's `read` of an image answers marker text and the picture rides the execute call's own MCP result as an image block (`Toolbox::call_parts`), so the model sees it as a direct `read` shows it; a background script's images are dropped. Every `execute` call saves its script to `<session dir>/exec/<N>.py` and appends `[saved exec #N]` (updated in place on `tools.rerun` so chained fixes keep earlier patches) until the Session is archived. It is the general way to an MCP server (the graph is also reached directly by `find`): `mcpclient.rs` loads `<config root>/mcp.json` (Claude shape, `include`/`exclude`/`enabled`/`summary`/`project`/`setup`; a `url` entry is refused), connects each stdio server with rmcp on first use, each in its own process group that is killed when the registry drops (a helper a server started does not outlive the Session's tool server), and exposes every tool as `tools.<server>.<tool>(...)` plus a bare alias when one server owns that name. `graph.rs` names the codebase-memory server and resolves its `project` argument (the entry's `project`, then `list_projects` matched by root path, then the path with separators as dashes), so a model never passes it. The daemon's `npx -y codebase-memory-mcp@<version>` graph entry runs the native `codebase-memory-mcp` instead when one is in a `ToolConfig::bin_dirs` directory (`PATH`, then `~/.local/bin`); npx is only the fallback. `setup` runs once per `CBM_CACHE_DIR`: a finished run writes `emberloop-setup.json` there with the setup it applied, and a later Session skips it while that record matches; a failed step reruns on the next connect. The marker is per cache dir, not per Project, because codebase-memory keeps its config in that dir.
- MCP startup: `McpRegistry::tools` and `tools_within` spawn one connect task per server and drain `(server index, connection)` results over one `tokio::sync::mpsc` channel, so tools come back in config-sorted server order and a slow server never delays a fast one. Each server's connect runs under its own `tokio::sync::Mutex<()>`, so concurrent `execute` and `call` share one child instead of spawning two. `tools_within(1500ms)` bounds `Toolbox::mcp_tools_soon`, and `call_within` bounds `find`'s graph calls; a connect that outlives a caller's wait keeps warming in a tracked task. `Drop for McpRegistry` aborts tracked unfinished connect tasks when the Session closes.
- `figcraft.rs` creates `design.figcraft`; `mcpclient/design.rs` connects every project-scoped FigCraft MCP process to the same durable server document. Private edit links live under `FIGCRAFT_LIVE_DIR`, keyed by canonical project-root hash and created under a cross-process file lock. `FIGCRAFT_SERVER_DATA` identifies the server key directory. Calls pump collaboration before and after tools, including inspection and pointer tools; files are snapshots, not a synchronization transport. Missing live configuration fails instead of starting a detached editor. `tests/figcraft_live.rs` is an explicit native check for bidirectional edits, project isolation and server restart recovery.
- `bash`: `sh -c` in the root, own process group, `EMBERLOOP_SESSION_DIR` exported (the Session directory), the runtime env file sourced first, the group is killed on timeout and again once the shell exits (a detached child does not outlive the call; `background` is the only way to keep one), 1 MiB output cap, `cat`/`head`/`tail`/`sed -n`/`grep -n` views feed the seen store. A foreground command asks `rtk rewrite` first and runs the answer when it exits 0 or 3; a missing rtk, a timeout or any other exit leaves the command as written. A command already starting with `rtk ` is never rewritten, which is the bypass.
- Blocking waits (`bash` foreground `timeout`, `background wait`, `execute` `timeout`) go through `Toolbox::call_secs`/`cap_secs`: each tool's own maximum, lowered to `ToolConfig::max_call_secs` when set. The `mcp` subcommand reads it from `EMBERLOOP_MAX_CALL_SECS`, which the Antigravity harness sets to 170 because Antigravity cuts an MCP call at 3 minutes and then exits.
- `background`: `list`, `read` (next byte offset), `wait`, `stop`; log files live in `spill/`; sources the same runtime env file. It starts `bash` commands and `execute` scripts with `background: true` alike: `BackgroundManager::spawn_with` takes the caller's builder plus a `keepalive` (`Box<dyn Any + Send>`) that is dropped when the job is reaped, so `execute`'s socket server and temp dir live exactly as long as its script (`-u`, so the log shows output as it lands; stderr joins stdout in the log; no timeout; a script adopted after a daemon restart keeps running but loses its `tools` calls, and its `tools.store` writes land immediately because no caller is left to flush on exit 0).
- `intercept`: the gate in front of `bash` (`intercept.rs`, first match wins, `EL_BASH_INTERCEPT=off` disables it). A command that belongs to another tool is refused before anything runs and the reply names that tool plus `Command not run: <line>`: `sed -i`/`perl -i`/`awk inplace` -> `edit`, inline Python (`-c`, stdin, heredoc) -> `execute`, `cat`/`echo`/`printf` with a file redirect and `tee` -> `write`, `nohup` and a trailing `&` -> `background: true`. It is routing, not security: a quoted `>` and `2>` pass, `python3 file.py` and `python3 -m http.server` stay allowed, and reads are never refused, so their views still feed the seen-line store `edit` checks. A refused command returns before the run and before `feed_views`, so it marks nothing seen.
- Runtime env: every shell sources `<config root>/env` (the daemon passes it; standalone falls back to `${XDG_CONFIG_HOME:-$HOME/.config}/emberloop-rs/env`) when that file exists, so editing it changes the next command with no rebuild and no daemon restart, and the prelude exports its path as `EMBERLOOP_ENV_FILE` so the policy can name the file without guessing the Session's HOME. `ToolConfig::env_file` overrides the path for tests. After that file, `env_prelude` appends the browser resolution from `browser.rs`: one Chrome found in Playwright's cache (any real or Session home), any `pi-homes/*/.agent-browser` cache, or `PATH`, newest version first, exported as `AGENT_BROWSER_EXECUTABLE_PATH`, plus defaults for `AGENT_BROWSER_ARGS` (V8 heap capped at 512 MB) and `AGENT_BROWSER_IDLE_TIMEOUT_MS` (5 minutes, after which the daemon closes the browser and frees its ~1.4 GB even when the model never runs `close`). A Session `HOME` is a fresh pi-home, so without the path every `agent-browser` call fails with "Chrome not found" and a model retries until it burns the turn. All three use `:=`, so the User's env file still wins. The path is resolved once per tool server (`OnceLock`).
- `todo`: the plan as one ordered list addressed by stable ids (`t1`, `t2`, …), one tool with `action` of `read`, `set`, `add`, `update`, `remove` or `clear`; statuses `pending`, `in_progress`, `completed`, `cancelled`, at most one in progress; ids never reused, `set` restarts them; persisted as `todos.json` in the Session directory (temp name plus rename).
- `ctx_search`: BM25-ranked word matches over the Session's spill chunks, with OR semantics, case folding, punctuation splitting, term-frequency saturation and length normalization; each hit has a pageable `ctx:<id>:<start>-<end>`. The scoring lives in `bm25.rs`, shared with `skill_search`. It scans existing spill files without a migration or new dependency. Unlike Go's FTS5 store, it has no Porter stemming, heading weighting, or persistent index.
- `overflow`: rendered output over `overflow_threshold` from `bash`, `execute` and `grep` is written to `<data root>/sessions/<id>/spill/<handle>` and replaced by a head/tail summary naming `ctx:<handle>`. `read` no longer spills, so a model pages a file with `offset`/`limit` or asks for it whole with `:raw`. Handle lookup accepts the proxy's `c`-prefixed spelling and the bare one interchangeably.
- `skill_search`: BM25 over every discovered skill that is not hidden (name, description, body headings and the first 2 KB of body). `query` is required; `limit` defaults to 5, max 20. Each hit gives name, origin, the description clipped to 150 characters and the absolute SKILL.md path; `read` loads it.
- `skills.rs`: `discover(global, project)` lists the `SKILL.md` folders under the global root and under `<project>/.agents/skills`, following symlinked folders. Project skills come first; a project skill hides a global skill of the same name. A malformed skill (frontmatter without a valid `name` and `description`, or a folder name that differs from `name`) is skipped with a warning. `origin` comes from `metadata.origin`, default `human`. A skill with `disable-model-invocation: true` in its frontmatter is `hidden`: the catalog and `skill_search` leave it out, `index` lists it as `name (hidden)`, and `read el://skills/<name>` still loads it, so the User starts it by name. `modules` drops a hidden member, so a module's line counts only the skills it lists and `index` shows the hidden skill under `ungrouped` as `name (hidden)`. `catalog(intro, global, project)` renders the frozen catalog: the intro, then `- name: description` lines capped at 50 and `N more skills: use skill_search` beyond that, ordered by root and then by latest `view` in each root's `.usage.jsonl`. `index(global, project)` is what `read` answers `el://skills` with: a `Skills: N. Modules: M.` line, one line per module with its member count and about text, then the names of the skills no module holds. It lists catalogues, never a skill body, so no harness truncates it. Reading a skill file (`read.rs` `skill_page`, `SKILL_PAGE_BYTES` 16 KB from the requested `offset`) returns one page and closes with `[skill continues at line N: read again with offset N]`, because pi cuts a model-facing MCP result over 20 KB in the middle and no setting raises that.
- `skill_manage`: an `ops` array applied all or nothing: `create`, `patch`, `write_file`, `remove_file`; no delete in v1. Only `metadata.origin: agent` skills change, and `create` forces that origin. Every touched skill is locked (`<root>/.locks/<sha256(name)>.lock`, `File::lock`) across its read-modify-write. A patch or write to an existing file is refused unless the current bytes were read in this Session (`Read <path> with read before changing it.`). Each change first copies the old file to `<root>/.backup/<name>/<unix-seconds>-<file>` and keeps ten per skill. Supporting files sit under `references/`, `templates/`, `scripts/` or `assets/` and may not reach outside through a symlink. A failing op undoes the earlier ones in the call. Each call appends one line to `<root>/.usage.jsonl`. `create` also maps the new skill in the target root's `skill-modules.json`: required once that root or the merged modules have any module (the refusal lists them), `""` leaves the skill ungrouped, a new module needs `module_about` (<=80 chars), and the mapping write is atomic, locked on the file name, and undone with the rest of the call.
- `skillstore.rs`: lock, backup, usage-log, `view` log and support-path helpers behind `skill_manage`. `read` of a `SKILL.md` directly under a skill root appends a `view` line. `bm25.rs`: the tokenizer and BM25 scorer shared by `ctx_search` and `skill_search`.
- `failedcalls.rs` (`retry_call`): `Toolbox` keeps `ToolConfig::retry_allowlist` (default `spawn`, `steer`, `write`, `edit`). Failing allowlisted calls write `{ tool, args }` (harness meta keys stripped) to `<spill_dir>/failed_calls/<N>.json` and append `[failed call #N] Retry with retry_call(id=N, ...)` after `denied_reason` checks. `FailedCallStore::record` returns `Ok(None)` for a payload over `128 KiB`; the caller logs `tracing::debug!` and returns the original error, and every record past the newest `50` is pruned on each record. `edit`'s stale-tag error records the `1..=min(200, line_count)` lines it shows at the file's live hash, so a tag-only `retry_call` needs no fresh `read`; the `ensure_unchanged` write-race error records nothing. `retry_call(id, set?, patches?)` applies `set` overrides (`null` removes keys) then exact-once `{ old, new }` string `patches` and re-dispatches through `Toolbox::call` (recording a new `#N` if the retried allowlisted call fails again).
## Limits

Seen-line snapshots persist in the Session's `seen/` directory (`state.json`,
atomic rename). A snapshot stores the full sha256 beside the 4-hex display tag,
and `edit` compares the full hash, so a 4-hex collision cannot pass a stale edit.

Background records persist `<id>.json` (pid, `/proc/<pid>/stat` start time, boot
id) next to `<id>.log`. A new `Toolbox` (daemon restart) adopts a process group
only when pid, start time and boot id all match; otherwise the handle is `lost`
and `stop` never kills an unknown process. An adopted exit reports
`exited (code unknown)`; an exit that happened while the daemon was down emits
its notice exactly once. `bash` is not a sandbox, and neither are `read`, `edit`
and `write`: only `grep` and `find` path arguments stay inside the project root.
